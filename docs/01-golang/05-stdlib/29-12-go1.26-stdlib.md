## 核心答案（30 秒版）

Go 1.26 标准库五个实用改进：

| 特性 | 所在包 | 核心价值 |
|------|--------|---------|
| **`Buffer.Peek(n)`** | `bytes` | 偷看缓冲区内容而不消耗数据，用于协议解析 |
| **`Dialer.DialTCP(ctx, ...)`** | `net` | 支持 Context 的 TCP 拨号，超时可取消 |
| **`errors.AsType[T](err)`** | `errors` | 编译期类型安全检查，替代 `errors.As` 指针传递陷阱 |
| **`strings.Join` 零分配** | `strings` | 非逃逸场景零分配，性能追平 strings.Builder |
| **`context.Cause(ctx)`** | `context` | 获取 Context 取消原因（Go 1.26 新增） |

## 深度展开

### 1. bytes.Buffer.Peek：协议解析神器

#### 1.1 出现背景

Go 1.26 为 `bytes.Buffer` 新增了 `Peek(n)` 方法。在此前，想要"偷看"缓冲区内容而不真正消费它，开发者只能自己记录位置或使用 `io.MultiReader` 包装，使用成本较高。

#### 1.2 Peek 语义

```go
// buf.Peek(n) 返回接下来 n 字节的视图，不移动读指针
// 有效范围：0 ≤ n ≤ buf.Len()
// 返回的 slice 在下次读写操作前有效（类似 io.Reader 的语义）

buf := bytes.NewBuffer([]byte("hello world"))
data, _ := buf.Peek(5)
fmt.Println(string(data)) // "hello"，但读指针未动
fmt.Println(buf.Len())    // 仍然 11
```

#### 1.3 典型场景：二进制协议解析

```go
// 读取自定义协议：header(4字节) + body(N字节)
// 使用 Peek 先读取 header，再决定读多少 body
func parseMessage(buf *bytes.Buffer) ([]byte, error) {
    if buf.Len() < 4 {
        return nil, errors.New("buffer too short")
    }
    // 先偷看 4 字节 header
    header, _ := buf.Peek(4)
    bodyLen := binary.BigEndian.Uint32(header)

    // 检查 body 是否完整
    if buf.Len() < 4+int(bodyLen) {
        return nil, errors.New("body not ready")
    }
    // 确认数据完整后，真正消费（Read）
    full := make([]byte, 4+bodyLen)
    _, err := buf.Read(full)
    return full, err
}
```

#### 1.4 与 io.LimitReader 对比

```go
// 旧写法：需要嵌套 Reader
r := io.LimitReader(buf, 5)
data := make([]byte, 5)
r.Read(data)

// 新写法：直接 Peek，更直观
data, _ := buf.Peek(5)
```

### 2. net.Dialer.Context：超时取消的 TCP 拨号

#### 2.1 出现背景

Go 1.26 之前，`net.Dialer` 的 `DialTCP` 方法**不支持 Context**。这导致 TCP 连接建立无法被 Context 取消，如果对方响应慢，goroutine 会一直阻塞。

#### 2.2 Go 1.26 新增方法

```go
// Go 1.26 新增：带 Context 的 TCP 拨号
func (d *Dialer) DialContext(ctx context.Context, network string, addr string) (*TCPConn, error)

// Go 1.26 新增：DialTCP 现在支持 ctx 参数
func (d *Dialer) DialTCP(ctx context.Context, laddr, raddr *TCPAddr) (*TCPConn, error)

// 示例：带超时的 TCP 连接
dialer := &net.Dialer{
    Timeout: 5 * time.Second,
}

ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()

conn, err := dialer.DialTCP(ctx, nil, &net.TCPAddr{
    IP:   net.ParseIP("10.0.0.1"),
    Port: 8080,
})
```

#### 2.3 实际应用：gRPC 连接管理

```go
// 生产级 gRPC 连接：超时控制 + 优雅取消
func dialGRPC(ctx context.Context, target string) (*grpc.ClientConn, error) {
    dialer := &net.Dialer{
        Timeout: 10 * time.Second,
    }

    // ctx 可用于取消拨号过程
    conn, err := dialer.DialContext(ctx, "tcp", target)
    if err != nil {
        return nil, fmt.Errorf("dial failed: %w", err)
    }

    return grpc.NewClient(target,
        grpc.WithContextDialer(func(ctx context.Context, addr string) (net.Conn, error) {
            return dialer.DialContext(ctx, "tcp", addr)
        }),
    )
}
```

#### 2.4 与 timeout 参数的区别

| 参数 | 作用范围 | 可取消 |
|------|---------|--------|
| `dialer.Timeout` | 整个拨号过程 | ❌ 无法中途取消 |
| `ctx` + `context.WithTimeout` | 同上，但可被 cancel() 主动取消 | ✅ 支持主动取消 |

### 3. errors.AsType[T]：编译期类型安全的错误检查

#### 3.1 旧 API 的问题

```go
// Go 1.25 及之前的 errors.As：需要传递指针的指针，容易出错
var target *MyError
if errors.As(err, &target) {  // &target 是 *MyError 类型
    // 处理 MyError
}

// 问题：如果传错类型或忘记取地址，编译期无法检测
errors.As(err, target)        // 编译错误：需要指针
errors.As(err, (*MyError)(nil)) // 绕过了类型检查
```

#### 3.2 AsType 泛型版本

```go
// Go 1.26 新增：errors.AsType[T]
// 泛型参数 T 自动推断，避免指针传递陷阱

if err, ok := errors.AsType[*MyError](err); ok {
    // err 是 *MyError 类型，ok 为 true 时 err != nil
    fmt.Println("got MyError:", err.Error())
}

// 对比旧写法：更简洁，类型推断更安全
var target *MyError
if errors.As(err, &target) { ... }
```

#### 3.3 编译期 vs 运行时

```go
// errors.As：运行时检查，传错类型不会编译报错（但可能有逻辑问题）
var target *string  // 传错了类型
errors.As(err, &target) // 编译通过，但逻辑错误

// errors.AsType：编译期类型检查
errors.AsType[*string](err) // 编译期确保 T 是具体错误类型指针
```

#### 3.4 实际应用：业务错误分类

```go
// 业务错误类型
type ValidationError struct {
    Field   string
    Message string
}

type AuthError struct {
    Code    int
    Message string
}

// 生产代码：清晰的错误分类
func handleError(err error) {
    switch {
    case errors.AsType[*ValidationError](err):
        fmt.Println("参数错误")
    case errors.AsType[*AuthError](err):
        fmt.Println("认证失败")
    default:
        fmt.Println("未知错误")
    }
}
```

### 4. strings.Join 零分配优化：告别 strings.Builder 执念

#### 4.1 背景

过去为了极致性能，开发者会刻意使用 `strings.Builder` 来拼接字符串，避免 `strings.Join` 的额外分配：

```go
// 旧观念：strings.Builder 性能更好
var b strings.Builder
for i, s := range parts {
    if i > 0 {
        b.WriteString(sep)
    }
    b.WriteString(s)
}
result := b.String()

// strings.Join 写法更简洁，但有人担心性能
result := strings.Join(parts, sep)
```

#### 4.2 Go 1.26 的优化

Go 1.26 优化了 `strings.Join` 的内部实现：

| 场景 | 优化前 | 优化后 |
|------|--------|--------|
| **非逃逸**（结果在函数内消费） | 多次分配 | **零分配** |
| **逃逸**（结果返回或传递给其他函数） | 多次分配 | **1次分配** |

```go
// Go 1.26：直接用 strings.Join，性能和 Builder 持平
parts := []string{"a", "b", "c", "d", "e"}
sep := ","

// 现在可以直接用 Join，不用手动 Builder 了
result := strings.Join(parts, sep)
fmt.Println(result) // "a,b,c,d,e"
```

#### 4.3 Benchmark 验证

```go
// Benchmark 结果（Go 1.26）
func BenchmarkJoin(b *testing.B) {
    parts := []string{"a", "b", "c", "d", "e"}
    for i := 0; i < b.N; i++ {
        _ = strings.Join(parts, ",")
    }
}
// 结果：与 strings.Builder 性能持平，且代码更简洁
```

#### 4.4 实际建议

```go
// Go 1.26 之前：追求性能用 Builder
var b strings.Builder
for i, s := range parts {
    if i > 0 {
        b.WriteString(sep)
    }
    b.WriteString(s)
}
return b.String()

// Go 1.26 及之后：直接用 Join
return strings.Join(parts, sep)
```

### 5. context.Cause：获取取消原因

#### 5.1 出现背景

Go 1.26 新增了 `context.Cause(ctx)` 函数，用于获取 Context 被取消的具体原因。在此之前，开发者只能从 `ctx.Err()` 获取通用错误（如 `context.Canceled`、`context.DeadlineExceeded`），无法区分"主动取消"还是"超时截止"。

#### 5.2 新增 API

```go
// Go 1.26: context.Cause 返回取消的根因
func Cause(ctx Context) error

// 与 ctx.Err() 的区别
ctx, cancel := context.WithTimeout(parent, 3*time.Second)
defer cancel()

select {
case <-ctx.Done():
    fmt.Println(ctx.Err())    // "context deadline exceeded"
    fmt.Println(context.Cause(ctx)) // "context deadline exceeded"（相同）
}
```

#### 5.3 实际场景：区分取消来源

```go
// 场景：HTTP 请求被取消，需要区分是客户端断开还是服务端超时
func handleRequest(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context()

    select {
    case <-time.After(10 * time.Second):
        // 故意延长处理时间，看 Context 是否被取消
        w.Write([]byte("ok"))
    case <-ctx.Done():
        // Go 1.26 可以清晰区分取消原因
        cause := context.Cause(ctx)
        switch cause {
        case context.Canceled:
            http.Error(w, "client cancelled", http.StatusRequestTimeout)
        case context.Deadlined:
            http.Error(w, "server timeout", http.StatusGatewayTimeout)
        default:
            http.Error(w, cause.Error(), http.StatusInternalServerError)
        }
    }
}
```

#### 5.4 与 signal.NotifyContext 配合

```go
// Go 1.26 推荐用法：signal 取消
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()

<-ctx.Done()
fmt.Println(context.Cause(ctx)) // 输出 "interrupt" 或 "terminated"
```

## 高频追问

### Q1: `Buffer.Peek` 返回的 slice 何时失效？

> `Peek` 返回的 slice 在下次 **Read/Write/Byte/WriteByte/Rune** 操作前有效。类似于 `io.Reader` 的语义，不能无限期持有。

```go
buf := bytes.NewBuffer([]byte("hello"))
data, _ := buf.Peek(3)
// 在这之前不能对 buf 做读操作
fmt.Println(string(data)) // "hel"
buf.ReadByte() // 破坏 Peek 结果
data2, _ := buf.Peek(3) // 重新 Peek
```

### Q2: `errors.AsType` 能否检查接口错误？

> 可以，只要接口满足 `error` 或自定义接口约束。

```go
type QueryError interface {
    GetQuery() string
    error
}

// 检查接口错误
if qe, ok := errors.AsType[QueryError](err); ok {
    fmt.Println("query:", qe.GetQuery())
}
```

### Q3: `strings.Join` 在循环内使用会每次分配吗？

> 不会。`strings.Join` 内部会预计算总长度，如果结果不逃逸，则零分配；如果结果逃逸，只分配一次（用于返回的 string）。

```go
// 非逃逸场景：结果在函数内消费，零分配
func process(parts []string) string {
    return strings.Join(parts, ",") // 零分配
}

// 逃逸场景：结果返回给调用方，一次分配
func joinAndReturn(parts []string) string {
    return strings.Join(parts, ",") // 分配 1 次
}
```
