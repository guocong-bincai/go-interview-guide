## 深度展开

### 1. 背景：为什么需要后量子密码学？

#### 1.1 量子计算的威胁

Shor 算法在理论上可以在多项式时间内破解 RSA、ECDSA、ECDH 等**基于大数分解和离散对数**的密码系统。

> **实用威胁时间线**：业界普遍认为 2030-2035 年量子计算机将具备破解当前公钥密码的能力（"Q-Day"）。

#### 1.2 迁移窗口

当前加密数据被"今天存储，明天解密"（Harvest-Now-Decrypt-Later）攻击：
- 情报机构现在收集加密流量，等量子计算机成熟后解密
- TLS 握手中的 RSA/ECDHE 密钥交换**现在就面临风险**

#### 1.3 NIST 后量子标准（2024 年最终化）

| 算法 | 类型 | 标准 |
|------|------|------|
| **ML-KEM**（原 Kyber）| 密钥封装（KEM）| NIST FIPS 203 |
| **ML-DSA**（原 Dilithium）| 数字签名 | NIST FIPS 204 |
| **SLH-DSA**（原 Sphincs+）| 哈希签名 | NIST FIPS 205 |
| **Falcon** | 格签名 | NIST（2025 后）|

### 2. crypto/mlkem：ML-KEM-768 原生实现

#### 2.1 核心概念：Key Encapsulation Mechanism（KEM）

KEM 不是直接加密数据，而是**在通信双方之间协商出一个共享密钥（Shared Secret）**：

```
Alice（接收方）:
  生成公钥（Encapsulation Key） + 私钥（Decapsulation Key）
  把公钥发给 Bob

Bob（发送方）:
  用 Alice 的公钥"封装"一个共享密钥 → 产生密文（ciphertext）
  把密文发回 Alice

Alice:
  用私钥"解封"获取同样的共享密钥
```

这正是 ECDH（X25519/P-256）密钥交换的格（Lattice）版本。

#### 2.2 API 详解

```go
import "crypto/mlkem"

// ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
// 接收方 Alice：生成密钥对
// ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
dk, err := mlkem.GenerateKey768() // 生成 ML-KEM-768 密钥对
if err != nil {
    log.Fatal(err)
}

// 导出公钥（1184 字节）发给 Bob
encapsulationKeyBytes := dk.EncapsulationKey().Bytes() // [1184]byte

// ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
// 发送方 Bob：用公钥封装共享密钥
// ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
// 从字节恢复公钥对象
ek, err := mlkem.NewEncapsulationKey768(encapsulationKeyBytes)
if err != nil {
    log.Fatal(err)
}

// 封装：生成 32 字节共享密钥 + 1088 字节密文
sharedSecret, ciphertext := ek.Encapsulate()
// sharedSecret: [32]byte ← 双方共享的密钥（用于后续对称加密）
// ciphertext:   [1088]byte ← 发送给 Alice

// ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
// 接收方 Alice：用私钥解封装获取共享密钥
// ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
decryptedSecret, err := dk.Decapsulate(ciphertext)
if err != nil {
    log.Fatal(err)
}

// 验证：双方得到完全相同的 sharedSecret
if !hmac.Equal(sharedSecret[:], decryptedSecret[:]) {
    panic("shared secret mismatch!")
}
```

#### 2.3 参数集对比

| 参数集 | 公钥大小 | 密文大小 | 共享密钥 | 安全级别（NIST）|
|--------|---------|---------|---------|--------------|
| **ML-KEM-512** | 800 B | 768 B | 32 B | 对应 AES-128 |
| **ML-KEM-768** | 1184 B | 1088 B | 32 B | 对应 AES-192 |
| **ML-KEM-1024** | 1568 B | 1568 B | 32 B | 对应 AES-256 |

> **面试加分点**：ML-KEM-768 是**推荐默认选择**，平衡安全级别和性能。ML-KEM-1024 用于最高安全场景，ML-KEM-512 用于性能敏感但安全级别要求不高的场景。

#### 2.4 与 ECDH/X25519 的直观对比

| 维度 | X25519（经典）| ML-KEM-768（后量子）|
|------|-------------|------------------|
| 基于难题 | 离散对数（可被量子破解）| 格上的 Module-LWE（抗量子）|
| 公钥大小 | 32 B | 1184 B（约 37x）|
| 密文大小 | 32 B | 1088 B（约 34x）|
| 共享密钥 | 32 B | 32 B（相同）|
| 性能 | 极快 | 较快（仍是合理量级）|

### 3. crypto/hpke：Hybrid Public Key Encryption（RFC 9180）

#### 3.1 HPKE 是什么？

HPKE = 混合公钥加密，将**经典 KEM（如 X25519）+ 后量子 KEM（如 ML-KEM）+ HKDF + AEAD**组合成统一框架。

**为什么需要 Hybrid？** 
- 纯后量子算法尚无 30 年安全证明
- Hybrid 模式 = 经典（前向安全）+ 后量子（抗量子）= 双重保险
- 任意一个被攻破，整个系统仍然安全

#### 3.2 一次性 API（One-Shot）

```go
import "crypto/hpke"

func oneShotDemo() {
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    // 组合套件：ML-KEM-768 + X25519 + HKDF-SHA256 + AES-256-GCM
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    kem := hpke.MLKEM768X25519() // Hybrid KEM：ML-KEM-768 + X25519
    kdf := hpke.HKDFSHA256()     // HKDF-SHA256
    aead := hpke.AES256GCM()     // AES-256-GCM

    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    // 接收方：生成私钥
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    recipientPrivateKey := kem.GenerateKey()
    publicKeyBytes := recipientPrivateKey.PublicKey().Bytes()

    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    // 发送方：用公钥加密
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    publicKey, _ := kem.NewPublicKey(publicKeyBytes)

    info := []byte("my-app-context-v1") // 应用上下文，防重放

    ciphertext, err := hpke.Seal(publicKey, kdf, aead, info, []byte("Hello, Alice!"))
    if err != nil {
        log.Fatal(err)
    }
    // ciphertext = encapsulated_key || seal(iv || ciphertext || tag)
    //             ≈ 32B(X25519) + 32B(ML-KEM) + 12B(iv) + N + 16B(tag)

    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    // 接收方：解密
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    plaintext, err := hpke.Open(recipientPrivateKey, kdf, aead, info, ciphertext)
    if err != nil {
        log.Fatal(err) // 密文被篡改或 key 不匹配
    }
    fmt.Printf("Decrypted: %s\n", plaintext)
}
```

#### 3.3 多轮对话 API（Multi-Shot / Session-Based）

对于需要多次加密的场景（如同一个密钥用于多个消息），使用 `Sender`/`Recipient`：

```go
func multiShotDemo(publicKeyBytes []byte) {
    kem := hpke.MLKEM768X25519()
    kdf := hpke.HKDFSHA256()
    aead := hpke.AES256GCM()
    info := []byte("chat-protocol-v1")

    // 发送方：建立会话（只需要对方公钥 + info）
    publicKey, _ := kem.NewPublicKey(publicKeyBytes)
    encapsulation, sender, err := hpke.NewSender(publicKey, kdf, aead, info)
    if err != nil {
        log.Fatal(err)
    }

    // 发送加密消息（每条消息有独立 nonce，无需操心计数器）
    ct1, _ := sender.Seal(nil, []byte("Message 1")) // nil AAD
    ct2, _ := sender.Seal(nil, []byte("Message 2"))

    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    // 接收方：用 encapsulation + 私钥建立会话
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    recipientPrivateKey := kem.GenerateKey() // 实际应持久化保存
    recipient, _ := hpke.NewRecipient(encapsulation, recipientPrivateKey, kdf, aead, info)

    pt1, _ := recipient.Open(nil, ct1)
    pt2, _ := recipient.Open(nil, ct2)
    // ...
}
```

#### 3.4 HPKE 套件组合矩阵

| KEM（密钥封装）| KDF（密钥派生）| AEAD（对称加密）| 场景 |
|--------------|---------------|---------------|------|
| X25519（经典）| HKDF-SHA256 | AES-128-GCM | 兼容性好 |
| X25519 | HKDF-SHA256 | ChaCha20-Poly1305 | 无 AES 硬件场景 |
| **ML-KEM-768** | HKDF-SHA256 | AES-256-GCM | **推荐（Hybrid 推荐）** |
| **ML-KEM-768X25519** | HKDF-SHA256 | AES-256-GCM | **最强安全（Hybrid）** |
| ML-KEM-1024 | HKDF-SHA512 | AES-256-GCM | 最高安全级别 |

> **面试加分点**：HPKE 是 **RFC 9180** 标准，被 MLS（Messaging Layer Security，RFC 9420）、TLS 1.3 External PSK 模式、Certificate Transparency 等多个协议采用。理解 HPKE 就理解了现代安全协议的后量子迁移路径。

### 4. testing/cryptotest：密码学实现测试框架

#### 4.1 为什么需要它

密码学实现极难做到完全正确，边缘 case（如全零输入、空密钥、长度边界）极易引入漏洞。`testing/cryptotest` 提供一个**标准化测试框架**，确保你的 crypto 实现符合规范。

```go
import (
    "crypto/ecdsa"
    "crypto/elliptic"
    "testing/cryptotest"
)

func TestECDSA(t *testing.T) {
    // cryptotest 测试 ECDSA 实现的规范符合性
    cryptotest.TestECDSA(t, &ecdsa.P256())
    cryptotest.TestECDSA(t, &ecdsa.P384())
    cryptotest.TestECDSA(t, &ecdsa.P521())
}

func TestAES(t *testing.T) {
    cryptotest.TestAES(t)
}
```

## 高频追问

**Q1：为什么 ML-KEM 的密钥这么大（1184 字节），比 X25519（32 字节）大几十倍？**
> X25519 基于椭圆曲线离散对数，点的坐标就是 32 字节。ML-KEM 基于格的 LWE 问题，需要存储"密钥矩阵"和"噪声向量"，公钥本身就是一个 1184 字节的结构。这是算法本质决定的，不是实现问题。

**Q2：ML-KEM 的安全性有保证吗？**
> ML-KEM 是 NIST FIPS 203 标准，经过多轮密码分析竞猜（2017-2022）。其安全性基于"Module-LWE"问题的困难性，与格（Lattice）问题等价。虽然不是 30 年级别的安全验证，但已被全球密码学界广泛审查，是目前最成熟的后量子 KEM 方案。

**Q3：Hybrid 加密会不会让性能变得很慢？**
> 确实会有一定 overhead，但 ML-KEM-768 的 Encapsulate 只需约 10-20 万个时钟周期（具体因硬件而异），在现代 CPU 上是亚毫秒级别。对于 TLS 握手这种少量密钥交换操作，完全可接受。

**Q4：如何在生产环境中使用这些包？**
> - `crypto/mlkem`：直接用于密钥协商，适用于自定义安全协议
> - `crypto/hpke`：用于标准化混合加密，替换现有的 ECDH 密钥交换
> - 当前阶段（2026）：推荐使用 Hybrid 模式（X25519 + ML-KEM），保证既有前向安全又有抗量子能力
> - 标准库尚未内置 TLS 1.3 Hybrid 密钥共享，需等待 `crypto/tls` 包更新或使用 BoringSSL/Gnutls

**Q5：runtime/secret 包是做什么的？**
> Go 1.26 实验性引入 `runtime/secret` 包，提供安全擦除敏感数据（如密钥）的 API。在密码学代码中，密钥使用完毕后需要立即从内存清除，防止冷启动攻击（cold boot attack）和内存dump分析。
```go
import "golang.org/x/exp/runtime/secret"

func secureEraseDemo(key []byte) {
    // 将 key 的内存内容清零，防止密钥残留
    secret.Zero(key)
    // key 现在是全零，但仍然是 []byte（容量不变，只是内容被清除）
}
```
> 这是实验性 API，需通过 `GOEXPERIMENT=secret` 启用。
