# 服务网格（Service Mesh）

> 考察频率：★★★★☆  难度：★★★★★  关键词：Sidecar、数据面 vs 控制面、Envoy、mTLS、Ambient 模式

## 一、服务网格解决什么问题

微服务治理（超时、重试、熔断、限流、mTLS、链路追踪）如果写成 SDK，会带来：

- **多语言重复建设**：Go/Java/Python 各维护一套 SDK，行为不一致。
- **升级困难**：治理逻辑和业务代码一起发版，SDK 升级要推动所有业务方改依赖。
- **业务侵入**：业务代码被迫引入一堆治理依赖。

服务网格的思路：**把治理逻辑从业务进程里抽出来，下沉到和业务并排运行的 Sidecar 代理**，通过 iptables/eBPF 透明劫持流量，业务对治理"零感知"。

```
┌──────────── Pod A ────────────┐        ┌──────────── Pod B ────────────┐
│  [业务容器]  ⇄  [Envoy Sidecar]│──mTLS──►│  [Envoy Sidecar]  ⇄  [业务容器]│
└───────────────────────────────┘        └───────────────────────────────┘
        ▲                                        ▲
        └──────── 控制面（Istiod）：下发路由/证书/策略 ────────┘
```

## 二、数据面 vs 控制面（必考）

| 平面 | 组成 | 职责 |
|------|------|------|
| **数据面（Data Plane）** | 每个实例旁的 Sidecar（Envoy） | 拦截所有进出流量，做路由、LB、mTLS 加解密、限流、上报指标 |
| **控制面（Control Plane）** | Istiod / xDS 服务 | 配置下发、证书签发与轮换、服务发现、策略管理；**不碰业务流量** |

控制面通过 **xDS 协议**（LDS/CDS/RDS/EDS）把路由、集群、监听器配置推给 Envoy。Envoy 是 C++ 写的通用代理，性能接近 Nginx，并且支持 Wasm 插件扩展。

## 三、Service Mesh vs SDK（库模式）选型

| 维度 | SDK / 库模式 | Service Mesh |
|------|--------------|--------------|
| 接入成本 | 每个服务改代码、引依赖 | 零侵入（注入 Sidecar），存量服务也能纳管 |
| 性能开销 | 几乎无（同进程函数调用） | 多一跳，P99 增加约 1~3ms；资源翻倍（每 Pod 一个 Envoy） |
| 多语言 | 每种语言一套 SDK | 语言无关，统一策略 |
| 运维复杂度 | 低（无额外组件） | 高（Envoy/Istiod 版本、证书、调试链路变长） |
| 适用 | 单一技术栈、延迟敏感、团队规模小 | 多语言、异构、服务多、治理诉求强 |

> **务实结论**：Go 单栈团队通常先用 **SDK 治理（Kratos/go-zero 内置中间件）+ K8s Service**，只有在多语言、多团队、治理要求强时才上 Mesh。**不要为了 Mesh 而 Mesh**。

## 四、关键能力与面试延伸

| 能力 | 说明 |
|------|------|
| **mTLS（零信任）** | 控制面签发证书，Sidecar 之间双向 TLS，业务代码零改造；证书自动轮换 |
| **流量管理** | 金丝雀（按百分比）、A/B 测试（按 Header/用户）、故障注入（延迟/错误） |
| **可观测性** | Sidecar 天然采集 4 层指标，无需业务埋点；但**链路追踪仍需上下文透传 Header** |
| **Sidecar vs Ambient** | Sidecar 每 Pod 一个代理，资源占用高；Istio **Ambient 模式**改用节点级 ztunnel + 按需 waypoint，省资源但能力是子集 |

**Sidecar 的固有痛点**：每个 Pod 多一个容器 → 内存/CPU 成本上升、启动顺序敏感（业务早于 Sidecar 启动会连不通）、调试链路变长（出问题要判断是业务还是代理）。这也是 Ambient/无 Sidecar 方案出现的动机。

## 五、面试常被追问

**Q：Sidecar 模式下，为什么业务刚启动时调用会失败？**
A：Sidecar 未就绪时，iptables 规则已劫持流量但代理还没监听端口 → 连接被拒。解决：用 `initContainer` 等待 Sidecar 就绪，或应用层加重试 + 启动探针，K8s 侧可用 `holdApplicationUntilProxyStarts`。

**Q：服务网格能替代链路追踪埋点吗？**
A：不能完全替代。Sidecar 只能采集**网络层** span（服务间调用），进程内的方法调用、DB/Redis 调用拿不到。要做到全链路，业务仍需 OpenTelemetry SDK，并保证 **W3C traceparent Header 透传**（Mesh 会透传，但应用要正确传播 context）。

## 面试话术

> **"服务网格本质是把治理能力从业务进程下沉到 Sidecar：控制面管配置和证书，数据面（Envoy）管流量，通信用 xDS 下发。它的最大价值是零侵入 + 多语言统一，代价是多一跳延迟、每 Pod 翻倍的资源、以及更长的排障链路。所以我的选型原则是：单一 Go 技术栈优先用 SDK 治理 + K8s Service，多语言异构、治理诉求强才上 Mesh。另外要澄清一点：Mesh 只能采到网络层 span，进程内调用还得靠 OpenTelemetry SDK 埋点。"**
