# 微服务拆分原则与粒度

> 考察频率：★★★★☆  难度：★★★★☆
> 关键词：微服务拆分、限界上下文、DDD、康威定律、绞杀者模式、分布式单体、拆分粒度

---

## 面试官考察意图

"你怎么把一个单体系统拆成微服务？"是微服务面试的**必考题**。面试官想考察：

1. 是否清楚**什么时候该拆、什么时候不该拆**（不是越多越好）
2. 是否有**方法论**（业务能力划分 / DDD 限界上下文 / 子域）
3. 是否知道拆分的**反模式**（分布式单体、服务间强耦合）
4. 有没有**演进式拆分**经验（绞杀者模式，而不是一步到位）

能讲出"先划分限界上下文，再按数据所有权拆分，最后通过绞杀者模式渐进落地"的候选人，通常就是他们要的人。

---

## 核心答案（30 秒版）

微服务拆分三问：

| 问题 | 答案 |
|------|------|
| **为什么拆？** | 单体在团队规模扩大后出现：部署耦合（改一行全量发）、技术栈绑定、扩展粒度粗、职责不清 |
| **按什么拆？** | 按**业务能力/限界上下文**拆，不是按技术层拆（不拆 controller/service/dao 层！） |
| **拆多大？** | 一个服务 = 一个业务能力域，能**独立部署、独立扩展、独立演进**；两个原则：数据不共享（独立库/表）、通信走接口（不直连库） |

**一句话：按业务边界（限界上下文）拆，每个服务拥有自己的数据，独立部署演进；拆不动就先绞杀者模式渐进迁移。**

## 深度展开

### 1. 先判断：该不该拆？（拆分的前置条件）

**不要为了拆而拆**。单体→微服务是"团队规模和组织复杂度逼出来的"，不是技术时髦：

| 该拆的信号 ✅ | 不该拆的信号 ❌ |
|-------------|---------------|
| 团队 > 2 个小组协作，发布互相踩 | 团队 5 人以内，单体迭代很快 |
| 某个模块频繁独立扩容（如搜索） | 业务简单稳定，无扩展瓶颈 |
| 发布频率高、全量回归成本大 | 一次性拆分，无演进计划 |
| 模块间数据边界清晰 | 模块间强耦合、表互相 join |

> 面试加分：**微服务的主要收益是组织收益（独立部署、独立团队、独立扩展），不是技术收益**。技术上是引入分布式复杂度（网络、一致性、运维）。

### 2. 拆分方法论：三步法

#### 第 1 步：识别业务能力（Business Capability）

从业务视角列出公司的核心能力，每个能力一个候选服务：

```text
电商系统业务能力：
├── 商品管理（商品中心）
├── 订单处理（订单中心）
├── 库存管理（库存中心）
├── 支付结算（支付中心）
├── 用户账户（用户中心）
├── 营销活动（营销中心）
└── 物流履约（履约中心）
```

#### 第 2 步：用 DDD 限界上下文（Bounded Context）收敛边界

同一个概念在不同上下文里含义不同（如"商品"在商品中心和营销中心的字段、状态完全不同）。**限界上下文 = 领域模型的边界 = 服务的边界**。

```text
订单上下文（Order Context）         支付上下文（Payment Context）
┌─────────────────────────┐       ┌─────────────────────────┐
│ Order {                 │       │ Payment {               │
│   orderId, status,      │       │   paymentId, orderId,   │
│   amount, buyerId       │       │   channel, status       │
│ }                       │       │ }                       │
│ "订单状态": CREATED→PAID │       │ "支付状态": PENDING→SUCCESS│
└─────────────────────────┘       └─────────────────────────┘
         │ 通过事件/接口通信，不共享表，不共享领域对象
```

**判定边界是否正确的试金石**：
- 两个上下文之间是否有**明确的数据所有权**？（谁的表谁能改）
- 跨上下文的交互是否只有**接口/事件**，没有直接数据库访问？
- 一个上下文的变更是否需要另一个上下文一起发布？（需要 = 边界划错了）

#### 第 3 步：按数据归属确定服务边界（Data Ownership）

**谁拥有数据，谁拥有服务**。一个服务必须独占自己的数据存储：

| 反模式 ❌ | 正确做法 ✅ |
|---------|-----------|
| 服务A 直接查服务B 的库表 | 服务A 调服务B 的 API/事件 |
| 多个服务共享一个库（库级共享） | 逻辑隔离（分库）或物理隔离 |
| 服务间通过数据库 join 聚合数据 | 通过 API 聚合或 CQRS 读模型 |

### 3. 拆分粒度：多大算合适？

**粒度没有标准答案，但有两个判定原则**：

1. **独立部署原则**：一个服务改动可以独立发布，不需要和其他服务联动
2. **团队规模原则**：每个服务至少有一个小团队（2~5 人）长期维护，服务数 ≈ 团队数

```text
常见粒度误区：
❌ 拆太细（函数级）：10 个服务互相调，一个下单要跨 6 个服务 → 分布式事务地狱
❌ 拆太粗（模块级）：其实还是单体，只是把 controller 拆出去
✅ 合适粒度：一个服务能独立完成一个业务能力闭环（如"订单+库存扣减"服务内完成，
   而不是"订单服务"调"库存服务"同步扣减）
```

> 面试话术：**粒度不是按代码量，而是按"变更边界"——两个模块经常一起改，就不该拆开；几乎不一起改，就可以拆。**

### 4. 演进式拆分：绞杀者模式（Strangler Pattern）

**不要一步到位重写**，用绞杀者模式渐进迁移：

```text
阶段1：单体 + 新功能用微服务
┌─────────────┐
│   单体系统    │ ← 新增功能直接做成独立微服务
└──────┬──────┘
       │ 调用
  ┌────▼────┐
  │ 新服务B  │
  └─────────┘

阶段2：逐个模块从单体剥离
┌─────────────┐    ┌──────────┐
│   单体系统    │ →  │ 服务A(已剥离) │
│ (瘦身中)     │    │ 服务B(已剥离) │
└─────────────┘    └──────────┘
每个模块：建新服务 → 双写/接口适配 → 流量切换 → 删除旧代码

阶段3：单体消失，全部微服务化
```

**绞杀者模式核心**：每次只迁移一个模块，迁移期间新旧并存（新服务写，双写或同步旧库），验证通过再切流量删旧代码。

### 5. 拆分后的治理配套（拆完不是结束）

| 维度 | 必须配套的能力 |
|------|--------------|
| 通信 | RPC 框架（gRPC）+ 超时/重试/熔断（见服务治理篇） |
| 数据一致性 | 分布式事务方案：本地消息表 / 事务消息 / Saga（见分布式模块） |
| 可观测性 | 指标 + 日志 + 链路追踪（TraceID 贯穿） |
| 部署 | CI/CD + 无损发布 + 灰度 |
| 团队 | 服务所有权明确（一个服务一个团队，康威定律） |

## 高频追问

### Q1：微服务的优缺点？
> 优点：独立部署、独立扩展、技术栈自由、故障隔离、团队自治。缺点：分布式复杂度（网络不可靠、一致性难）、运维成本高、调试困难、性能损耗（远程调用）。**核心是组织收益 vs 技术成本的权衡。**

### Q2：什么是康威定律？
> "设计系统的组织，最终产生的设计等价于组织内部的沟通结构。"简单说：**服务边界应该对齐团队边界**——两个团队共同维护一个服务必然扯皮，一个服务分给两个团队 = 变相单体。

### Q3：服务拆了之后，跨服务的数据一致性怎么保证？
> 原则：**优先避免跨服务事务**（边界划分正确时大部分操作是单服务内事务）。不可避免时按场景选：最终一致性用本地消息表/事务消息（推荐，可靠投递 + 消费幂等）；强一致用 TCC/Saga（代价高，慎用）。详见分布式模块事务篇。

### Q4：拆完变成"分布式单体"怎么办？
> 分布式单体 = 服务间大量同步调用 + 共享数据 + 一起发布，比单体更差。治理：收敛调用链（同步调用改事件异步化）、划定数据所有权、坚持独立发布纪律。

### Q5：按技术层拆（controller/service/dao 各自成服务）为什么是错的？
> 因为技术层拆分没有业务边界：改一个订单功能要同时改 controller 服务、service 服务、dao 服务并一起发布——部署耦合没解决，还多了网络开销。
