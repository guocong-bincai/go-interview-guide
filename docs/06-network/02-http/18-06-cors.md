# CORS 跨域原理与解决方案：同源策略、预检请求与 Go 实战

> 考察频率：★★★★★  优先级：P1
> 关键词：同源策略、CORS、简单请求、预检请求 Preflight、OPTIONS、Access-Control-*、携带 Cookie、Nginx 处理、JSONP

---

## 🎯 面试官考察意图

跨域问题几乎是**每个后端都真真切切踩过**的问题：前端本地调试报 `blocked by CORS policy`、生产环境加了新域名后登录态丢失、OPTIONS 请求 403 导致全部接口挂掉。

面试官考察的深度层次：
1. **初级**：知道跨域是浏览器同源策略导致的，知道要加 `Access-Control-Allow-Origin`；
2. **中级**：能分清简单请求和预检请求，知道 OPTIONS 是浏览器自动发的；
3. **高级**：知道「预检结果缓存」「带 Cookie 时不能用 `*`」「为什么加 `allow-credentials` 后前端还要开 `withCredentials`」，能讲清楚**服务端加 CORS 头到底解决了什么、没解决什么**。

---

## ⚡ 核心答案（30秒）

**跨域 = 浏览器同源策略的产物，不是服务器的问题。**

| 概念 | 说明 |
|------|------|
| **同源** | 协议 + 域名 + 端口 三者完全相同 |
| **谁在拦截** | **浏览器**（服务端其实收到了请求、也返回了响应，只是浏览器不给 JS 看） |
| **解决方式** | 服务端返回 `Access-Control-Allow-Origin` 等 CORS 头，告诉浏览器"这个源我允许" |
| **简单请求** | 直接发，靠响应头判断是否放行 |
| **非简单请求** | 先发 `OPTIONS` 预检，通过后才发真实请求 |

**一句话话术：**
> 浏览器出于同源策略会拦截跨域响应，服务端需要返回 CORS 响应头来"授权"；非简单请求浏览器会先发一个 OPTIONS 预检，我们要保证 OPTIONS 请求能被正确响应且不被鉴权中间件拦掉。

## 🔬 深度展开

### 1. 同源策略是什么，为什么要它

**同源 = 协议 + 域名 + 端口 全部相同。**

```
https://api.example.com:443/data

✅ 同源：https://api.example.com:443/other
❌ 跨域：http://api.example.com        （协议不同）
❌ 跨域：https://api.example.com:8080  （端口不同）
❌ 跨域：https://www.example.com       （域名不同，子域也算）
```

**为什么要有同源策略：**
如果没有它，你在浏览 `evil.com` 时，页面里的 JS 可以：
- 用你的 Cookie 去请求 `bank.com/api/transfer`（CSRF）；
- 读取 `bank.com` 的响应内容，把你的余额、订单偷走（CSRF 拿不到响应，但 CORS 放开就能拿到）。

所以同源策略的核心目的是**阻止不同源的 JS 读取彼此的数据**（注意：是"读取"，不是"发送"）。

**关键认知：跨域请求在多数情况下是发出去了的。**

```
前端 JS ──请求──► 浏览器 ──发出──► 服务端（收到了、处理了、返回了 200）
                     │
                     └── 检查响应头没有 Access-Control-Allow-Origin
                         └── 拦截，JS 只拿到一个 TypeError
```

**这意味着：跨域的"写操作"可能已经生效了！** 所以你不能靠"跨域被拦截"来保护写接口——真正该做的是 CSRF Token / SameSite Cookie / 鉴权。

### 2. 简单请求 vs 非简单请求（预检）

**简单请求（不会触发 OPTIONS）必须同时满足：**

| 条件 | 取值 |
|------|------|
| 方法 | `GET`、`HEAD`、`POST` 之一 |
| 请求头 | 只能是 `Accept`、`Accept-Language`、`Content-Language`、`Content-Type` 等 CORS 安全头 |
| `Content-Type` | 只能是 `text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded` |
| 其它 | 请求中没有 `ReadableStream`，没有事件监听器 |

> ⚠️ 关键：**`Content-Type: application/json` 不是简单请求！** 所以几乎所有前后端分离的 JSON 接口都会触发 OPTIONS 预检。

**预检流程：**

```
浏览器                                    服务端
  │                                         │
  │ ── OPTIONS /api/user ──────────────────►│  预检请求
  │    Origin: https://www.example.com      │
  │    Access-Control-Request-Method: POST  │
  │    Access-Control-Request-Headers:      │
  │      content-type,authorization         │
  │                                         │
  │ ◄── 204 No Content ─────────────────────│  预检响应
  │    Access-Control-Allow-Origin: https://www.example.com
  │    Access-Control-Allow-Methods: GET,POST,PUT,DELETE,OPTIONS
  │    Access-Control-Allow-Headers: Content-Type,Authorization
  │    Access-Control-Max-Age: 86400        │  ← 预检结果缓存 24h
  │                                         │
  │ ── POST /api/user （真实请求）─────────►│
  │    Origin: https://www.example.com      │
  │ ◄── 200 + Access-Control-Allow-Origin ──│  真实响应也必须带 CORS 头
```

**要点：**
- 预检是**浏览器自动发的**，前端代码里看不到，只能用抓包工具看到；
- 预检响应**不需要业务逻辑**，只返回头即可（204 最快）；
- **真实请求的响应也必须带 CORS 头**，否则依然被拦截（很多人只给 OPTIONS 加了头，忘了业务响应）；
- `Access-Control-Max-Age` 能减少预检次数，但浏览器有上限（Chrome 约 2 小时，Firefox 24 小时）。

### 3. 核心响应头详解

| 响应头 | 作用 | 坑 |
|--------|------|-----|
| `Access-Control-Allow-Origin` | 允许哪个源。`*` 表示任意源 | **带 Cookie 时不能用 `*`**，必须回显具体 Origin |
| `Access-Control-Allow-Methods` | 允许的方法（仅预检需要） | 逗号分隔无空格也可，但规范建议 `GET, POST` |
| `Access-Control-Allow-Headers` | 允许的请求头（仅预检需要） | 漏了自定义头（如 `X-Token`）→ 预检失败 |
| `Access-Control-Allow-Credentials` | 是否允许携带 Cookie | 设为 `true` 时 Origin 不能是 `*` |
| `Access-Control-Expose-Headers` | 哪些响应头允许 JS 读取 | 默认 JS 只能读 6 个"安全头"（`Cache-Control`、`Content-Language`、`Content-Type`、`Expires`、`Last-Modified`、`Pragma`）；读不到 `X-Request-Id`、`Content-Disposition` 就是这个原因 |
| `Access-Control-Max-Age` | 预检结果缓存秒数 | 0 或不设则每次都预检 |
| `Vary: Origin` | 告诉 CDN/缓存按 Origin 区分缓存 | **最容易漏的一个**，见下方踩坑 |

### 4. 带 Cookie 的跨域（最容易被问倒的部分）

需要**三端配合**才能真正带上 Cookie：

```javascript
// 1) 前端：fetch 必须显式声明
fetch('https://api.example.com/user', {
  method: 'GET',
  credentials: 'include',   // axios 里是 withCredentials: true
});

// 2) 服务端：必须回显具体 Origin + 允许凭证
// Access-Control-Allow-Origin: https://www.example.com   ← 不能是 *
// Access-Control-Allow-Credentials: true

// 3) Cookie 本身：跨站场景要过 SameSite
// Set-Cookie: sid=xxx; SameSite=None; Secure; Domain=.example.com
```

**三个高频坑：**

| 现象 | 原因 |
|------|------|
| `Credentials not supported with wildcard` | `Allow-Origin: *` 与 `Allow-Credentials: true` 冲突 |
| `withCredentials: true` 发了但 Cookie 没带 | Cookie 的 `SameSite=Lax`（默认）阻止跨站发送，需 `SameSite=None; Secure` |
| 请求带 Cookie 了但响应读不到 | 少配 `Expose-Headers` |

> 💡 更根本的建议：**跨站 Cookie 的 `SameSite=None` 会带来 CSRF 风险**，最稳的架构是**同源部署**（用 Nginx 反向代理把 `/api` 转到后端，前端只访问自己的域名），从根上消除跨域。这也是大厂前端 BFF 层的价值之一。

### 5. Vary: Origin —— 90% 的人会漏的坑

如果你动态回显 Origin（而不是返回 `*`），**必须加 `Vary: Origin`**：

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://www.example.com
Vary: Origin
```

**不加的后果：**
CDN 或代理缓存了第一个请求的响应（`Allow-Origin: https://a.com`），之后 `https://b.com` 的请求拿到的还是这个缓存响应 → 浏览器发现 Origin 不匹配 → 跨域失败。

现实表现：**"首页能打开、某个接口偶发跨域失败、刷新一下又好了"** —— 这类偶现问题八成是 `Vary` 缺失。

### 6. Go 中间件完整实现（可直接抄）

```go
package middleware

import (
	"net/http"
	"strings"
)

// CORSConfig CORS 配置
type CORSConfig struct {
	AllowedOrigins   []string // 精确白名单，支持 "*"（不推荐与凭证同用）
	AllowedMethods   []string
	AllowedHeaders   []string
	ExposedHeaders   []string
	AllowCredentials bool
	MaxAge           int // 秒
}

func DefaultCORSConfig() CORSConfig {
	return CORSConfig{
		AllowedOrigins:   []string{"https://www.example.com", "https://admin.example.com"},
		AllowedMethods:   []string{"GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"},
		AllowedHeaders:   []string{"Content-Type", "Authorization", "X-Request-Id"},
		ExposedHeaders:   []string{"X-Request-Id"},
		AllowCredentials: true,
		MaxAge:           86400,
	}
}

func CORS(cfg CORSConfig) func(http.Handler) http.Handler {
	allowAll := len(cfg.AllowedOrigins) == 1 && cfg.AllowedOrigins[0] == "*"

	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			origin := r.Header.Get("Origin")
			if origin == "" {
				next.ServeHTTP(w, r) // 非跨域请求，直接放行
				return
			}

			// 动态回显 Origin —— 必须配合 Vary: Origin 防缓存串味
			w.Header().Add("Vary", "Origin")

			allowed := false
			switch {
			case allowAll:
				allowed = true
				if !cfg.AllowCredentials {
					w.Header().Set("Access-Control-Allow-Origin", "*")
				} else {
					// 带凭证时不能用 *，回显 Origin
					w.Header().Set("Access-Control-Allow-Origin", origin)
				}
			default:
				for _, o := range cfg.AllowedOrigins {
					if strings.EqualFold(o, origin) {
						allowed = true
						w.Header().Set("Access-Control-Allow-Origin", origin)
						break
					}
				}
			}

			if !allowed {
				// 不直接 403，让业务照常返回，只是浏览器会拦截并报错
				// 好处：方便排查（能拿到真实响应），坏处：写操作可能已生效
				next.ServeHTTP(w, r)
				return
			}

			if cfg.AllowCredentials {
				w.Header().Set("Access-Control-Allow-Credentials", "true")
			}
			if len(cfg.ExposedHeaders) > 0 {
				w.Header().Set("Access-Control-Expose-Headers", strings.Join(cfg.ExposedHeaders, ", "))
			}

			// 预检请求：到此为止，不往下走业务逻辑
			if r.Method == http.MethodOptions &&
				r.Header.Get("Access-Control-Request-Method") != "" {
				w.Header().Set("Access-Control-Allow-Methods", strings.Join(cfg.AllowedMethods, ", "))
				// 回显请求的 header 列表（或返回白名单）
				if reqHeaders := r.Header.Get("Access-Control-Request-Headers"); reqHeaders != "" {
					w.Header().Set("Access-Control-Allow-Headers", reqHeaders)
				}
				if cfg.MaxAge > 0 {
					w.Header().Set("Access-Control-Max-Age", itoa(cfg.MaxAge))
				}
				w.WriteHeader(http.StatusNoContent) // 204，最快
				return
			}

			next.ServeHTTP(w, r)
		})
	}
}

func itoa(n int) string {
	// 简单实现，避免引入 strconv 干扰阅读
	if n == 0 {
		return "0"
	}
	var buf [20]byte
	i := len(buf)
	for n > 0 {
		i--
		buf[i] = byte('0' + n%10)
		n /= 10
	}
	return string(buf[i:])
}
```

**注册顺序很重要：**

```go
mux := http.NewServeMux()
// ... 路由注册

// CORS 必须在鉴权中间件之前，否则 OPTIONS 预检会被鉴权拦下返回 401
handler := CORS(DefaultCORSConfig())(AuthMiddleware(mux))
```

> ⚠️ **生产最常见的 CORS 事故**：OPTIONS 预检请求没带 `Authorization` 头（浏览器不会给预检带业务头），结果被鉴权中间件拦成 401/403，预检失败，所有跨域接口全挂。解决：CORS 中间件放在鉴权之前，或鉴权中间件里显式跳过带 `Access-Control-Request-Method` 的 OPTIONS 请求。

### 7. Nginx 层处理 CORS（推荐做法）

网关层统一处理，业务代码零侵入：

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    set $cors_origin "";
    if ($http_origin ~* "^https://(www|admin)\.example\.com$") {
        set $cors_origin $http_origin;
    }

    # 预检直接由 Nginx 返回，不打到后端
    if ($request_method = OPTIONS) {
        add_header Access-Control-Allow-Origin      $cors_origin always;
        add_header Access-Control-Allow-Methods     "GET, POST, PUT, PATCH, DELETE, OPTIONS" always;
        add_header Access-Control-Allow-Headers     "Content-Type, Authorization, X-Request-Id" always;
        add_header Access-Control-Allow-Credentials "true" always;
        add_header Access-Control-Max-Age           86400 always;
        add_header Vary                             "Origin" always;
        return 204;
    }

    location / {
        add_header Access-Control-Allow-Origin      $cors_origin always;
        add_header Access-Control-Allow-Credentials "true" always;
        add_header Access-Control-Expose-Headers    "X-Request-Id" always;
        add_header Vary                             "Origin" always;

        proxy_pass http://backend;
    }
}
```

> 注意 `add_header ... always` 的 `always`：不加的话，4xx/5xx 响应不会带 CORS 头，浏览器只会报"跨域"，把真实的 500 错误藏起来，排查难度陡增。

### 8. 其他跨域方案对比

| 方案 | 原理 | 适用 | 缺点 |
|------|------|------|------|
| **CORS** | 服务端返回授权头 | ✅ 现代标准方案 | 需要服务端配合，预检有额外 RTT |
| **Nginx 反向代理** | 让前端同源访问 `/api` | ✅ 最稳，无跨域 | 需要运维配置，多环境维护 |
| **BFF/网关聚合** | 前端只调 BFF 同源接口 | ✅ 微服务架构 | 多一层 |
| **JSONP** | `<script src>` 不受同源限制 | ⚠️ 只支持 GET，已淘汰 | 无错误处理、有 XSS 风险 |
| **`document.domain`** | 同主域跨子域降级 | ❌ 已废弃（Chrome 115+ 移除） | 安全性差 |
| **postMessage** | 跨窗口通信 | iframe/多窗口场景 | 不是 HTTP 层面的跨域方案 |

> 面试加分：直接说「JSONP 是历史产物，现代方案是 CORS + 同源代理；真正的前后端分离项目推荐 BFF 或网关层统一解决，业务代码不该关心跨域」。

## ❓ 高频追问

### Q1：跨域请求，服务端到底收到了吗？

**收到了。** 除了被浏览器 `blocked` 的场景（如 Private Network Access），普通跨域请求浏览器都会真的发出去，服务端会正常处理并返回，只是浏览器不给 JS 结果。

所以：
- **`GET` / `POST` 的副作用可能已经产生**（比如跨域的下单请求真的创建了订单）；
- 不能用"跨域被拦"当安全边界；防 CSRF 要用 Token / SameSite / Origin 校验。

### Q2：为什么 OPTIONS 请求有时候会 404 或 405？

- 路由框架没有为 OPTIONS 方法注册 handler（比如用了只匹配 GET/POST 的路由）；
- 鉴权中间件先执行，OPTIONS 没有凭证 → 401；
- Nginx 没配 `if ($request_method = OPTIONS)`，直接透传给后端，后端又不认。

**统一修法**：网关层拦截 OPTIONS 直接返回 204，永远不打到业务。

### Q3：`Access-Control-Allow-Origin` 能不能用通配符匹配子域？

**不能。** 规范只支持三种值：`*`、`null`、或一个精确的 Origin。想要"允许所有 `*.example.com`"必须在服务端**判断并回显具体 Origin**：

```go
if strings.HasSuffix(origin, ".example.com") {
    w.Header().Set("Access-Control-Allow-Origin", origin) // 回显，不能写 *.example.com
}
```

**安全提醒**：不要用 `strings.HasSuffix(origin, "example.com")`（`evilexample.com` 会被放行），要检查 `origin == "example.com" || strings.HasSuffix(origin, ".example.com")`。

### Q4：预检请求会带上 Cookie 吗？

**不会。** 预检请求是浏览器自己发的，不携带业务凭证（Cookie、Authorization）。所以预检的鉴权必须在 CORS 中间件层放行，不能依赖业务鉴权。

### Q5：为什么生产环境建议用同源代理而不是 CORS？

1. **没有预检 RTT**，省一次往返；
2. **Cookie 同源**，不用处理 `SameSite=None` 带来的 CSRF 风险；
3. **运维统一管理**：CDN、WAF、限流配置都只针对一个域名；
4. **更安全**：浏览器层面根本不暴露后端域名。
