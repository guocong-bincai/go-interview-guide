# Redis 主从复制原理：全量同步与增量同步（psync）

> 考察频率：★★★★★  难度：★★★★☆
> 关键词：主从复制、psync、全量同步、增量同步、repl_backlog_buffer、复制偏移量、runid

## 面试官考察意图

主从复制是 Redis 高可用的基石（哨兵和集群都依赖它），大厂必考。面试官想确认：

1. 是否理解主从复制的目的（读写分离、数据备份、高可用基础）
2. 能否讲清全量同步（第一次连接）和增量同步（断线重连）的完整流程
3. 是否知道 psync 命令、runid、复制偏移量 offset、repl_backlog_buffer 的作用
4. 能否说明什么情况下增量同步会退化为全量同步

---

## 核心答案（30 秒版）

**主从复制 = 主节点写数据，异步复制到从节点**，实现读写分离和数据备份。

同步分两种：

- **全量同步**（第一次连接）：从节点发 `psync ? -1` → 主节点 `bgsave` 生成 RDB 快照发给从节点 → 从节点清空旧数据、加载 RDB → 主节点把生成 RDB 期间的新写命令（存在复制缓冲区）补发给从节点
- **增量同步**（断线重连）：从节点发 `psync {runid} {offset}` → 主节点检查 offset 是否还在 **repl_backlog_buffer**（复制积压缓冲区）中 → 在则只发送断线期间的写命令（增量）；不在则退化为全量同步

关键点：**runid 变了或 offset 超出 backlog 范围 → 全量同步；否则增量同步。**

## 深度展开

### 1. 为什么需要主从复制？

```
单机 Redis 的瓶颈：
  - 单点故障：机器挂了服务直接不可用
  - 读并发受限：一台机器扛不住大量读请求

主从架构（一主多从）：
        ┌─────────┐
        │ Master  │  ← 只负责写
        └────┬────┘
        ┌────┴────┐
     ┌──┴──┐  ┌──┴──┐
     │S1读│  │S2读│  │S3读│  ← 分摊读请求
     └─────┘  └─────┘  └─────┘
```

主从复制解决的问题：
1. **读写分离**：主写从读，分摊读压力
2. **数据备份**：从节点是主节点的数据副本，可做容灾
3. **高可用基础**：主节点宕机后，哨兵可以把从节点提升为新主节点

### 2. 命令配置

```bash
# 从节点配置（redis.conf 或命令行）
replicaof 127.0.0.1 6379   # 指定主节点

# 或命令行动态配置
SLAVEOF 127.0.0.1 6379
```

建立连接后，主从之间保持**长连接**，主节点把写命令实时推送给从节点。

### 3. 全量同步（Full Resync）：第一次连接

```
从节点                             主节点
  │                                  │
  │ 1. psync ? -1（不知道 runid 和 offset）│
  │ ────────────────────────────────> │
  │                                  │ 2. 生成 RDB 快照（bgsave 子进程）
  │                                  │    同时把新写命令记入复制缓冲区
  │ 3. FULLRESYNC {runid} {offset}   │
  │ <──────────────────────────────── │
  │ 4. 收到 RDB 文件                  │
  │ 5. 清空自己所有数据                │
  │ 6. 加载 RDB 文件                  │
  │                                  │ 7. 发送复制缓冲区中积压的写命令
  │ <──────────────────────────────── │
  │ 8. 执行这些命令，追上主节点进度     │
  │                                  │
  │ ───── 此后进入增量同步模式 ──────── │
```

**要点**：
- `psync ? -1`：`?` 表示不知道主节点 runid，`-1` 表示偏移量未知（第一次）
- 主节点返回 `FULLRESYNC {runid} {offset}`，从节点保存这两个信息
- RDB 生成期间的新写入 → 复制缓冲区（replication buffer），RDB 发送完后补发
- 全量同步代价大：主节点 IO 压力大、从节点要清空重载数据

### 4. 增量同步（Partial Resync）：断线重连

```
从节点                               主节点
  │                                    │
  │ 1. psync {runid} {offset}（带上次进度）│
  │ ─────────────────────────────────> │
  │                                    │ 2. 校验 runid 是否一致？
  │                                    │    ┌─ 不一致 → 全量同步
  │                                    │    └─ 一致 → 检查 offset 是否在
  │                                    │       repl_backlog_buffer 中
  │                                    │       ├─ 在 → 3. CONTINUE
  │                                    │       │     发送 offset 之后的命令
  │                                    │       └─ 不在 → 全量同步
  │ 3. CONTINUE                        │
  │ <───────────────────────────────── │
  │ 4. 收到断线期间丢失的写命令          │
  │ 5. 执行命令，追上主节点             │
```

**要点**：
- 从节点记住上次的 `{runid, offset}`，断线重连时带上
- **repl_backlog_buffer**：主节点维护的环形缓冲区（默认 1MB），记录最近的写命令
- offset 还在 backlog 内 → 增量同步（快，只传断线期间的数据）
- offset 已被覆盖 / runid 变了 → 全量同步（慢，传全量数据）

### 5. 复制积压缓冲区（repl_backlog_buffer）

```
repl_backlog_buffer（环形，默认 1MB）：
┌────────────────────────────────────┐
│ ... | 命令 | 命令 | 命令 | 命令 | ... │
└────────────────────────────────────┘
      ↑                        ↑
  oldest offset             newest offset
```

- 作用：记录主节点的写命令，供从节点断线重连后增量同步
- **默认 1MB 太小**：写频繁时很快被覆盖，断线一会儿就退化为全量同步
- 调优：`repl-backlog-size` 建议设为 `(主节点每秒写入量) × (可容忍断线秒数)`，比如每秒 1MB 写入、容忍 10 分钟断线 → 600MB

```bash
# redis.conf
repl-backlog-size 512mb
```

### 6. 主从复制的延迟与一致性

- 复制是**异步**的：主节点写成功后立即返回，不等待从节点确认
- 主从延迟：网络 + 从节点执行命令时间
- 延迟过大问题：
  - 读从库读到旧数据（业务上需要容忍或走主库）
  - 用 `INFO replication` 查看 `master_repl_offset` 和从节点 offset 的差距

### 7. 高频追问

**Q1：全量同步为什么用 RDB 不用 AOF？**
RDB 是二进制快照，文件小、加载快；AOF 是命令日志，文件大、重放慢。全量同步用 RDB 效率最高。

**Q2：复制风暴是什么？**
主节点挂了，大量从节点同时请求全量同步 → 主节点瞬间 IO 压力爆表。解决方案：从节点级联复制（从节点再挂从节点），或使用哨兵限制同时升级的数量。

**Q3：主从切换后数据会丢吗？**
可能丢。异步复制下主节点挂了但还没来得及同步的写命令会丢失。缓解：`min-replicas-to-write` 配置（写前要求至少 N 个从节点确认），但会牺牲可用性。

**Q4：Redis 主从复制和 Cluster 集群什么关系？**
Cluster 的每个主节点也有自己的从节点做复制备份；哨兵模式也依赖主从复制实现故障转移。**主从复制是所有高可用方案的地基。**

## 面试话术

- **初级**："主从复制就是主节点写、从节点读，第一次全量同步 RDB，之后增量同步命令。"
- **中级**："psync 命令带 runid 和 offset。第一次发 `psync ? -1` 全量同步；断线重连发 `psync {runid} {offset}`，offset 在 repl_backlog_buffer 里就增量同步，不在就退化全量。"
- **高级**："repl_backlog_buffer 默认才 1MB，写频繁的库要调大，否则网络抖动一下就全量同步，把主节点 IO 打爆。复制是异步的，主从延迟要监控 master_repl_offset 差距。从节点级联可以防复制风暴。"
