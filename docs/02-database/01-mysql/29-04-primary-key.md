# MySQL 主键选择：自增主键 vs UUID vs 雪花 ID

> 考察频率：★★★★☆  难度：★★★☆☆
> 关键词：自增主键、UUID、雪花算法、聚簇索引、页分裂、顺序写、分布式 ID

## 面试官考察意图

主键设计直接影响 InnoDB 聚簇索引的性能，是"看似简单实则必考"的高频题。面试官想确认：

1. 是否理解主键与聚簇索引的关系（主键决定数据物理排列）
2. 能否说清自增主键为什么"快"（顺序写入、无页分裂）
3. 能否说清 UUID 主键为什么"慢"（随机写入、页分裂、索引膨胀）
4. 能否结合分布式场景给出合理选型（雪花 ID 等）

---

## 核心答案（30 秒版）

**InnoDB 表是聚簇索引组织表（IOT），主键就是数据的物理存储顺序。**

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **自增主键** | 顺序写入、无页分裂、索引体积小 | 单库单机、可被遍历 | 单体应用、内部系统 |
| **UUID** | 全局唯一、生成简单、不暴露量 | 随机写入页分裂严重、索引膨胀（36 字符） | 极少用，基本是反面教材 |
| **雪花 ID** | 全局唯一、趋势递增、高性能 | 依赖时钟、需要部署方案 | 分布式/分库分表场景 |

**面试结论**：单机用自增主键；分布式/分库分表用雪花 ID（或类似趋势递增 ID）；UUID 直接做聚簇主键是性能陷阱。

## 深度展开

### 1. 为什么主键如此重要？

InnoDB 的数据是**按主键顺序**物理存储的（聚簇索引）：

```
聚簇索引结构（简化）：

主键 1 → 行数据
主键 2 → 行数据
主键 3 → 行数据
...
叶子节点之间按主键顺序用双向链表连接
```

因为数据页按主键顺序排列，**主键的生成方式直接决定写入性能**。

### 2. 自增主键：顺序写入

```sql
CREATE TABLE user (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    name VARCHAR(64),
    PRIMARY KEY (id)
);
```

**为什么快？**
- 新插入的行主键递增 → 永远追加到数据文件末尾（当前页）→ **顺序写**
- 当前页写满了就申请新页，几乎不会触发**页分裂**
- 二级索引的叶子节点存主键，BIGINT 只有 8 字节，索引体积小

**缺点**：
- 单库单机生成，无法用于分库分表（每个库的自增值会重复）
- 可通过 `SELECT MAX(id)` 被遍历，暴露业务量（可用 `AUTO_INCREMENT` 起始值+步长缓解）
- 预分配间隙：事务回滚后 ID 不回收

### 3. UUID 主键：为什么是性能陷阱？

```sql
-- ❌ 反面教材
CREATE TABLE log (
    id CHAR(36) NOT NULL,  -- UUID 字符串
    ...
    PRIMARY KEY (id)
);
```

**三个致命问题**：

1. **随机写入 → 页分裂**：UUID 完全随机，新行会插入到已有数据的中间位置 → 不断触发页分裂 → 数据页碎片化 → 随机 IO

```
自增写入：  [1][2][3][4][5] ← 追加
UUID 写入：[3][1][5][2][4] ← 随机插入中间，反复分裂
```

2. **索引膨胀**：CHAR(36) 存储 36 字节，比 BIGINT 大 4.5 倍。**每个二级索引都冗余一份主键** → 二级索引体积爆炸

3. **缓存失效**：数据分散在大量数据页中，Buffer Pool 命中率下降

**什么时候可以接受 UUID？**
- 业务要求主键绝对不可预测（防遍历）
- 可以改用 **UUID 存储为 BINARY(16)**（去掉横线转二进制），体积减半
- 或者用 UUID 做业务字段，另设自增主键（两层结构）

### 4. 雪花 ID：分布式场景的标准答案

```go
// Snowflake ID 结构（64 bit）：
// ┌─1bit─┬──41bit──┬──10bit──┬──12bit──┐
// │ 符号  │ 时间戳    │ 机器ID  │ 序列号   │
// └──────┴─────────┴─────────┴─────────┘
// 时间戳：毫秒级，可用约 69 年
// 机器ID：10 bit，支持 1024 台机器
// 序列号：12 bit，同毫秒内支持 4096 个 ID
```

**特点**：
- **全局唯一**：时间戳+机器ID+序列号组合
- **趋势递增**：ID 主体是时间戳 → 写入接近顺序 → 页分裂很少（比 UUID 好太多）
- **高性能**：本地生成，无网络 IO（对比：数据库自增需要回表查询）

**注意**：雪花 ID 是"趋势递增"不是"严格递增"，所以主从切换后可能出现小幅度回退（时钟回拨问题需要处理）。

**生产实现**：
- 简单场景：自研（注意时钟回拨、机器ID分配）
- 成熟方案：美团 Leaf、百度 UidGenerator、开源 snowflake 库

### 5. 选型决策树

```
业务需要分库分表/多机房全局唯一？
├─ 是 → 雪花 ID（或 Leaf/UidGenerator）
└─ 否 → 单库单机？
    ├─ 是 → 自增主键 BIGINT（推荐）
    └─ 否（但未来可能分库）→ 提前用雪花 ID
```

**补充场景**：
- 分库分表中间件（ShardingSphere）支持多种分布式 ID 策略（SNOWFLAKE/UUID/自定义）
- 业务上不想暴露数据量 → 自增主键配合 `ROW_NUMBER()` 或脱敏处理对外

### 6. 高频追问

**Q1：自增主键为什么用 BIGINT 不用 INT？**
INT 上限 21 亿，高并发几年就可能耗尽；BIGINT 上限 922 亿亿，几乎不可能耗尽。且 BIGINT 只比 INT 多 4 字节，代价极小。

**Q2：MyISAM 和 InnoDB 的主键设计有区别吗？**
MyISAM 是堆表，主键不影响物理存储；InnoDB 是聚簇表，主键直接决定数据排列。所以 InnoDB 下主键设计影响更大。

**Q3：没有主键的表会怎样？**
InnoDB 会优先选第一个非空唯一索引作为聚簇索引；都没有则隐藏生成 6 字节的 `rowid`。所以**建表务必显式指定主键**。

**Q4：自增主键在分库分表后怎么办？**
各库自增值会冲突，需要全局 ID 方案：雪花 ID、号段模式（Leaf segment）、Redis INCR 等。

## 面试话术

- **初级**："单机用自增主键，分布式用雪花 ID，UUID 做主键性能差。"
- **中级**："InnoDB 是聚簇索引表，主键决定数据物理排列。自增主键顺序写入无页分裂；UUID 随机插入频繁页分裂、索引膨胀；雪花 ID 趋势递增，兼顾全局唯一和写入性能。"
- **高级**："UUID 做聚簇主键是性能陷阱：页分裂+二级索引冗余膨胀（36字节 vs 8字节）。雪花 ID 要处理时钟回拨。生产上分库分表推荐号段模式（Leaf）或雪花，单机就是 BIGINT 自增，建表必须显式指定主键。"
