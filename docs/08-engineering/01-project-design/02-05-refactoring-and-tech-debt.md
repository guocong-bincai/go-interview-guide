# 重构与技术债治理

> 考察频率：★★★★★  优先级：P0

## 面试官考察意图

考察候选人的**系统长期维护能力**和**技术判断力**。
初级工程师：代码写完能用就行，不考虑未来变化。
高级工程师：**主动识别技术债，权衡重构成本和收益，在业务压力和技术质量之间找到平衡点**。
面试官想看你：不只是能写好代码，还要能在业务快速迭代的压力下保持代码质量，甚至让它变得更好。

---

## 核心答案（30 秒版）

技术债 = **用技术上的"债"换业务上的"快"**，但债总要还，否则利息会压垮系统：

| 技术债类型 | 典型表现 | 利息 |
|-----------|---------|------|
| 明知故欠 | 为了赶上线跳过代码审查，用 if-else 临时方案 | 维护成本指数增长 |
| 无意之债 | 业务变了，设计没跟上 | 功能开发越来越慢 |
| 积累之债 | 多人协作，风格不统一，接口随意 | bug 越来越多 |

**重构 vs 重写决策树：**
```
系统能正常跑吗？
├─ 能 → 重构（保持运行，逐步替换）
│         ├─ 核心模块 + 高风险 → 绞杀者模式
│         └─ 独立模块 + 低风险 → 平行运行 + 开关切换
└─ 不能 → 评估重写成本
          ├─ 重写 < 3个月 → 可接受重写
          └─ 重写 > 6个月 → 绞杀者模式（否则业务等不起）
```

## 深度展开

### 1. 什么算技术债，如何量化影响

**技术债的量化维度：**

```go
// 技术债评分 = 影响范围 × 修复难度 × 复现频率
score := impactScope * fixDifficulty * recurrenceFreq
```

| 维度 | 低（1分） | 中（3分） | 高（9分） |
|------|----------|----------|----------|
| 影响范围 | 单接口 | 单服务 | 多服务/全局 |
| 修复难度 | < 1天 | 1天~1周 | > 1周 |
| 复现频率 | 月均1次 | 周均1次 | 每天都有 |

**实操量化方法：**

```
1. 统计近 3 个月的 bug，按模块分类
   → 找出 bug 重灾区（某模块 bug 占 40%+ 就是高债）

2. 测量功能开发时间趋势
   → 如果一个功能以前 3 天能做完，现在需要 1 周，说明债在积累

3. 代码审查复杂度
   → 如果一个 PR 有 30+ 评论，其中 15+ 是代码风格/设计问题，说明债务严重
```

**技术债雷达图（面试可以画）：**
```
        可维护性
           ↑       可扩展性
           │        ↗
           │      ↗
           │    ↗   ← 债最高
           │  ↗
           │↗________________→ 性能
           └───────────────→
              稳定性   可读性
```

### 2. 重构 vs 重写：怎么决策

**Martin Fowler 的建议：** 重写是风险最高的重构方式，优先考虑重构。

**决策框架：**

```
                         系统是否还能演化？
                          /
             能 ───────────────────────────── 不能
              ↓                                       ↓
    业务是否接受短期停机？                重写不可避免
    /            \                    （做好充分测试和灰度）
是 → 绞杀者模式   否 → 持续重构
     低风险逐步替换
```

**什么时候可以重写：**
- 原有系统完全不可维护（代码没人能看懂，改任何地方都可能引发未知 bug）
- 业务可以接受 2~3 个月的功能冻结
- 新技术栈相比旧栈有 10 倍以上的效率提升

**什么时候只能重构：**
- 系统还在高频迭代，停不下来
- 团队对原有业务逻辑理解不深（重写 = 重写 bug）
- 涉及复杂的外围系统对接

### 3. 绞杀者模式、双写、灰度重构

#### 绞杀者模式（Strangler Fig Pattern）

**核心理念：** 不要拆掉旧楼，在它旁边盖新楼，等新楼稳定了再拆旧楼。

```
旧系统（遗留）        过渡期               新系统
┌──────────┐       ┌──────────┐
│  旧逻辑   │       │ API GW   │
└────┬─────┘       └────┬─────┘
     │                   ↓
     │            ┌──────────┐  ┌──────────┐
     │            │ 新服务    │  │ 旧服务    │（还没迁移完的）
     │            └────┬─────┘  └────┬─────┘
     │                 └─────┬──────┘
     ↓                        ↓
┌──────────┐           ┌──────────┐
│ 旧数据库 │           │ 新数据库  │
└──────────┘           └──────────┘
```

**Go 实战示例（API Gateway 路由逐步迁移）：**
```go
func SetupRouter() *gin.Engine {
    r := gin.Default()

    // 新模块走新服务
    r.GET("/api/v2/users/:id", userService.GetUser)
    r.POST("/api/v2/orders", orderService.CreateOrder)

    // 还没迁移的模块，继续走旧服务（未来会删除这段）
    r.Any("/api/v1/*path", proxy.ToLegacy("http://legacy-monolith"))

    return r
}
```

#### 双写策略（Dual Write）

新旧系统同时写入，逐步把流量切到新系统：

```
Step 1: 写操作同时写入新旧数据库
Step 2: 新系统读流量逐步从 0% → 10% → 50% → 100%
Step 3: 旧系统读流量同步减少
Step 4: 旧系统写流量归零，下线旧系统
```

**风险：**
- 双写期间如果有一边写入失败，可能导致数据不一致
- 需要补偿机制处理不一致

#### 灰度重构

功能开关（A/B Testing）控制新旧逻辑：

```go
// 功能开关控制重构进度
func GetUser(ctx context.Context, userID string) (*User, error) {
    if features.IsEnabled("new_user_service", userID) {
        return newUserService.Get(ctx, userID)
    }
    return legacyUserService.Get(ctx, userID)
}
```

### 4. 如何不停机重构核心系统

**原则：一切换流量的操作都要可回滚**

```
步骤：
1. 先把新系统部署上线，但新系统不接任何流量（Shadow Mode）
2. 旧系统流量照常，记录每笔请求的预期结果
3. 用影子流量验证新系统结果是否与旧系统一致（对账）
4. 灰度：1% 流量切到新系统，持续观察 24h
5. 逐步扩大：10% → 30% → 50% → 100%
6. 全量切完后，旧系统保留 7 天再下线（留紧急回滚窗口）
```

### 5. 如何说服业务接受技术债偿还成本

**技术债的危害要量化：** 不能只说"代码难看"，要说"这个债务导致每个新功能开发周期变长 3 天，按我们每月 10 个新功能算，相当于每个月损失 30 个工程师工作日"。

**把技术债还债变成业务收益：**
```
❌ 错误说法："我们需要花 2 周重构订单模块"
✅ 正确说法："如果不重构，下个大促（预计 3 个月后）的订单系统扩容成本是 50 万。
             重构后我们预计能把扩容成本降到 15 万以内，所以我建议现在花 2 周重构。"
```

**让业务参与决策：**
> "重构和欠着不还，两个选项的风险和成本分别是 X 和 Y，您看我们怎么安排？"
把技术决策变成业务决策，让业务方有参与感和责任感。

### 6. 面试中如何讲技术债治理案例

**STAR 法则讲技术债案例：**

```
S（情境）：当时订单系统已经 3 年没重构，每次加新功能都要 2 周以上，
          而且线上 bug 有 40% 来自订单模块。

T（任务）：我需要把这个系统的技术债还掉，同时不能影响正常业务迭代。

A（行动）：
  1. 用代码指标工具（SonarQube）量化了债务：订单模块圈复杂度 > 30 的函数有 47 个
  2. 按影响范围和修复难度做了优先级排序
  3. 用绞杀者模式，先拆分出了"订单创建"这个高频子模块用新架构重写
  4. 用功能开关控制流量，从 1% 灰度到 100% 用了 3 周
  5. 稳定后开始逐步迁移其他子模块

R（结果）：
  - 订单模块的新功能开发周期从 2 周缩短到 3 天
  - 订单模块的线上 bug 率下降了 70%
  - 整个重构历时 4 个月，没有发生一次线上故障
```

## 高频追问

**Q：业务催得紧，怎么平衡质量和速度？**
> 核心是**分类处理**：
> - 核心链路（支付、下单）：质量优先，宁可延期
> - 非核心功能：可以欠债，但必须记录下来
> - 无论什么情况：监控和告警不能欠，这是底线

**Q：团队里没人愿意改旧代码，怎么办？**
> 1. 建立"童子军规则"：离开时让代码比来时更干净（每次 PR 至少解决一个小问题）
> 2. 用技术指标（代码覆盖率、圈复杂度）让问题可见
> 3. 把技术债清理和绩效挂钩

**Q：重构到一半，业务又加了新需求怎么办？**
> 停止重构，合并分支。重构必须是一个连续的、不被打断的过程。如果被打断了，宁可放弃这次重构，重新评估。

## 一句话记忆
**技术债治理 = 用量化指标找出债务最高的地方，用绞杀者模式在运行中逐步替换，用业务语言说服业务方接受还债成本。**
