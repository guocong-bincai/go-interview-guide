# 故障复盘（Postmortem）方法论

> 考察频率：★★★★★  优先级：P0

## 面试官考察意图

考察候选人的**线上稳定性保障能力和学习复盘能力**。
初级工程师：故障修完就完了，下次可能犯同样错误。
高级工程师：**修完故障后，还要搞清楚为什么发生，怎么避免下次**，并推动系统性改进。
面试官想看：你不只是能修 bug，而是能通过一次故障让整个系统变强。

---

## 核心答案（30 秒版）

故障复盘的核心是 **RCA（Root Cause Analysis） + 系统性改进**：

| 步骤 | 目的 |
|------|------|
| 时间线还原 | 搞清楚故障的传播链 |
| 根因 vs 诱因 vs 放大器 | 区分不同层面的问题 |
| 5 Why 追问 | 从表象追问到根本原因 |
| 改进项分类（短/中/长期）| 把复盘变成行动 |
| 文档沉淀 | 让全团队从这次故障中学习 |

**一句话：** 好的复盘不是为了追责，而是让"坏事"变成系统进化的燃料。

## 深度展开

### 1. 什么是 Postmortem，为什么不能只停留在修 bug

**Postmortem（事后复盘）** 是 Google/SRE 体系中的核心理念：

```
修 bug 解决的是单个问题
Postmortem 解决的是"为什么会有这类问题"
```

**反面案例（面试中怎么讲）：**
> "当时服务挂了 30 分钟，我们紧急扩容了 10 台机器恢复了。修完之后就继续开发了。"
> → 这类回答说明你只是"救火队员"，没有系统性思维。

**正确示范：**
> "服务挂了 30 分钟，根本原因是定时任务在凌晨 2 点做全表扫描导致 MySQL 负载飙升。除了扩容，我们发现定时任务其实可以改成增量同步，MySQL 也缺少慢查询监控。最终我们推动了 3 项改进：任务改增量、添加慢查询告警、引入压测流程。"

**为什么修完 bug 就完事是危险的：**
- 同类故障会重复发生
- 团队没有形成知识积累
- 下次故障来临时，同样手忙脚乱

### 2. RCA：5 Why / 鱼骨图

#### 5 Why 分析法

**原则：从现象追问到根本原因，通常需要追问 4~6 次**

案例：用户下单失败
```
Q1：为什么下单失败？
A1：因为库存服务不可用了。

Q2：为什么库存服务不可用？
A2：因为 Redis 集群有一个节点挂了。

Q3：为什么 Redis 节点挂了？
A3：因为服务器内存耗尽，触发 OOM。

Q4：为什么会内存耗尽？
A4：因为有一条大 key（2GB）的 HGETALL 操作，把内存打爆了。

Q5：为什么会有 2GB 的大 key？
A5：因为运营在后台配置了一个包含 10 万 SKU 的营销活动，但这个 key 没有设置过期时间。

                           ↓ 根因
   "大 key 没有设置过期时间 + 缺少 bigkey 监控告警"
```

#### 鱼骨图（ Ishikawa Diagram）

用于结构化归类可能原因：

```
                    故障/问题
            ┌───────┼───────┐
            ↓       ↓       ↓
         人员      流程    技术
         ───      ───     ───
    培训不足    SOP缺失   代码bug
    操作失误    审批缺漏   架构缺陷
                      配置错误
                      监控缺失
```

### 3. 故障时间线如何还原

**信息来源（按可靠性排序）：**
```
1. 日志（最可靠）： grep 时间点关键词
2. 监控/告警记录：告警触发时间、恢复时间
3. 运维操作记录：谁在什么时间做了什么操作
4. 用户反馈：外部视角的故障表现
5. 内存（最不可靠）：当事人口述（可能有偏差）
```

**时间线模板：**
```
T-00:00  监控触发 CPU 告警（P99 > 2000ms）
T-00:03  on-call 工程师收到告警，开始排查
T-00:07  发现是某定时任务导致的全表扫描
T-00:12  执行 kill 命令终止慢查询，CPU 开始下降
T-00:15  监控显示 P99 恢复到 50ms，确认恢复
T-00:20  发出故障通报（Incident declared）
T-02:00  发布故障复盘报告
```

### 4. 如何区分根因、诱因与放大器

这是高级工程师区别于初级工程师的关键：

| 概念 | 定义 | 举例 |
|------|------|------|
| **根因（Root Cause）** | 最早导致问题发生的那个事件 | 大 key 没有 TTL |
| **诱因（Contributing Cause）** | 让问题更容易发生的条件 | 缺少 bigkey 监控 |
| **放大器（Amplifier）** | 让问题变得更严重的因素 | 没有熔断机制，小问题扩散成大故障 |

**实操案例：**
```
背景：服务 A 响应变慢，导致调用服务 A 的服务 B 也开始超时，最终 30% 的请求失败。

分析：
- 根因：服务 A 的数据库连接池配置过小（maxConns=10）
- 诱因：没有连接池监控，连接耗尽前没有告警
- 放大器：服务 B 没有熔断机制，服务 A 变慢导致 B 的线程池也被拖满

改进策略：
- 根因修复：扩大连接池（maxConns=100）+ 上线连接数监控
- 诱因修复：添加数据库连接数告警（>80% 阈值）
- 放大器修复：服务 B 接入熔断器（参考 Hystrix/Sentinel）
```

### 5. 改进项如何分短期 / 中期 / 长期

| 时间维度 | 定义 | 交付时间 | 示例 |
|---------|------|---------|------|
| **短期（Quick Win）** | 立竿见影，风险低 | 1~3 天 | 加监控告警、调整超时参数 |
| **中期（ проектирование）** | 需要设计和小规模验证 | 1~4 周 | 重构慢查询、引入熔断 |
| **长期（战略）** | 需要评审、设计、灰度 | 1~3 月 | 架构拆分、引入多活 |

**改进项优先级矩阵：**
```
            高复现率
                ↑
                │
   短期+高频 → 优先做   长期+高频 → 规划做
                │
   短期+低频 → 快速做   长期+低频 → 跳过或接受风险
                │
                ↓
            低复现率
```

## 高频追问

**Q：如何推动团队做真正的复盘而不是走过场？**
> 关键是把复盘和绩效考核解耦（Google SRE 的做法）：
> "复盘是为了学习，不是为了追责。如果团队害怕复盘，复盘就失去了意义。"

**Q：故障和线上问题有什么区别，什么时候不需要正式复盘？**
> 故障 = 影响了用户/造成资损，需要正式复盘。
> 轻微问题 = 没影响用户，可以放到迭代回顾会里简单讨论。

**Q：如何避免复盘出来的改进项不了了之？**
> 1. 每项改进必须有 owner 和 deadline
> 2. 在下次的项目 sync 会上同步进展
> 3. 超过 2 周未完成的改进项要升级汇报

---

## 一句话记忆
**故障复盘 = 5 Why 追问根因 + 区分诱因和放大器 + 短期止血、中期加固、长期治本。**
