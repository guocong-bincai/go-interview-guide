# 代码生成工程化：go:generate 体系与生成代码的工程约束

> 考察频率：★★★☆☆  优先级：P1
> 关键词：go:generate、代码生成、stringer、mockgen、protoc、生成文件校验、CI 一致性

## 面试官考察意图

"你们项目用 `go:generate` 吗？生成的代码怎么管？"——中等偏上的工程素养题。它考察候选人是否理解**「手写重复代码是 bug 的温床，能用工具生成就不要手写」**这条工程原则，以及是否踩过生成代码的协作坑：

1. `go:generate` 的**语义与边界**（它只是注释标记 + 一条 shell 命令）；
2. 常见生成场景（枚举 `String()`、mock、Protobuf、深拷贝、embed）；
3. **生成物要不要提交**、**CI 怎么保证生成物与源一致**（这是高级考点）。

**核心立场：生成代码要么进仓库并被 CI 校验一致性，要么完全不进仓库由构建期生成——绝不能"一半提交一半不提交"，那是协作灾难。**

---

## 核心答案（30 秒版）

`go:generate` 是**一条特殊注释**，`go generate ./...` 会扫描源码里的 `//go:generate` 并**按顺序在对应目录执行命令**（命令是任意 shell 命令，不是 Go 特有的）。

```go
//go:generate stringer -type=Status   // 为枚举生成 String() 方法
//go:generate mockgen -source=repo.go -destination=mock_repo.go -package=mocks
//go:generate protoc --go_out=. --go-grpc_out=. user.proto
```

**四条工程纪律**：

1. **枚举一定有 `String()`**（`stringer`），别再手写 `switch` 映射；
2. **Protobuf/Mock/深拷贝等生成物提交进仓库**，方便 review 与离线构建；
3. **CI 跑 `go generate ./... && git diff --exit-code`**，任何人改了源没重生成 → 直接失败；
4. **生成物文件头标注 `// Code generated ... DO NOT EDIT.`**，禁止手改（`golangci-lint` 可检测）。

**一句话**：**生成代码是"编译产物的半成品"——它应该由源文件唯一决定；只要它和源不一致，就是 bug。**

## 深度展开

### 一、`go:generate` 的真实语义（很多人搞错）

- 它**不是构建系统**，`go build` 不会触发它；必须显式 `go generate`；
- 命令在**该文件所在目录**执行，可用 `$GOFILE`、`$GOARCH` 等环境变量；
- 生成顺序：`go generate ./...` 按包路径字典序；**包内有依赖时要用 `-run` 分步控制**；
- 命令里最好用 `go run <tool>` 或 `go tool <tool>`，避免依赖开发机全局安装的工具版本。

```go
// ✅ 推荐：把工具依赖写进 go.mod，版本可复现
//go:generate go run go.uber.org/mock/mockgen -source=repo.go -destination=mock_repo.go -package=mocks

// Go 1.24+ 更推荐 go tool
//go:generate go tool mockgen -source=repo.go -destination=mock_repo.go -package=mocks
```

⚠️ **工具版本漂移**是最常见的坑：A 同事用 `mockgen@v0.3`、B 同事用 `v0.5`，生成的 mock 有细微差异，`git diff` 每天都有噪声。**解决：`go.mod` 里 `tool` 依赖固定版本**（Go 1.24 的 `go get -tool`），或用 `tools.go` + build tag 的经典做法。

### 二、五大高频生成场景

**1. 枚举 `String()`（stringer）**

```go
type Status int
const (
    StatusPending Status = iota
    StatusPaid
    StatusCancelled
)

//go:generate stringer -type=Status -linecomment
//
// 生成 status_string.go：
//   const _Status_name = "PendingPaidCancelled"
```

**2. Mock（mockgen）**——见 [单元测试 Mock 工程化](26-04-test-mock.md)。

**3. Protobuf（protoc / buf）**

```bash
buf generate   # 现代方案，比 protoc 手拼参数好太多
```

生成的 `*.pb.go`、`*_grpc.pb.go` **必须提交**，且**禁止手改**（手改会在下次生成时被覆盖，且 grpc 版本升级后可能对不上）。

**4. 深拷贝（deepcopy-gen / copier 生成）**

对含指针、slice、map 的复杂结构，手写深拷贝极易漏字段。生成器保证"新增字段自动覆盖"。

**5. `embed` 静态资源**

```go
//go:embed templates/*.html
var tmplFS embed.FS
```

严格说 `embed` 是编译指令不是 `go:generate`，但同属"声明式生成/打包"。

### 三、生成物管理：提交 vs 不提交

| 维度 | 提交进仓库（推荐） | 不进仓库 |
|------|--------------------|----------|
| 好处 | review 可见、离线可构建、CI 不依赖额外工具链 | 仓库小、无 diff 噪声 |
| 坏处 | 仓库变大、生成器版本升级产生大 diff | 每次构建都要装工具链，失败多、不可复现 |
| 适合 | Protobuf、mock、stringer（团队协作） | 大型中间产物、平台特定的代码 |

**关键结论**：**只要团队要 review 生成代码的变更（哪怕是"确认没意外变化"），就应该提交。** 后端 Go 项目 99% 的情况都应该提交。

### 四、CI 一致性校验（高级考点，必答）

```yaml
# .github/workflows/generate-check.yml
name: generate-check
on: [pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: '1.25' }
      - name: Regenerate
        run: go generate ./...
      - name: Ensure no diff
        run: |
          if ! git diff --exit-code; then
            echo "::error::生成代码与源文件不一致，请在本地执行 go generate ./... 并提交"
            git diff --stat
            exit 1
          fi
```

**这条 CI 规则的价值**：把"忘了重新生成"从**运行时事故**（接口调不通、String() 缺失 panic）变成 **PR 阶段的失败**。面试里能说出这条，基本可以锁定"有真实工程经验"。

### 五、生成代码的工程约束

1. **文件头标记**：Go 规范是 `// Code generated by <tool>; DO NOT EDIT.`，位于文件顶部、包注释之前；
2. **禁止手改**：可在 `golangci-lint` 里配置，或 CI 里 `git diff --name-only | grep '_gen.go\|.pb.go'` 检查是否有人在 PR 直接改生成文件（应改源）；
3. **`.gitattributes`**：

```gitattributes
*_gen.go    linguist-generated=true
*.pb.go     linguist-generated=true
```

让 GitHub 折叠生成文件的 diff，**review 聚焦源文件**（这条能显著提升 review 质量，面试加分）。

4. **生成文件不纳入覆盖率**：`go test -coverprofile` 时排除 `*.pb.go` / `*_gen.go`，否则覆盖率虚高；
5. **目录命名约定**：`internal/gen/` 或与源同目录加后缀 `_gen.go`，团队统一。

### 六、什么时候**不该**用代码生成

生成不是银弹，以下场景手写更好：

- **一次性脚本**（生成完就扔，不如直接写）；
- **逻辑频繁变化的代码**（源变生成物就变，diff 噪声大）；
- **生成器本身不稳定 / 社区不维护**（技术债）；
- **能靠泛型解决的**（Go 1.18+ 泛型可以替代一部分代码生成，如类型安全的容器，**不要为了生成而生成**）；
- **运行期反射可接受的性能场景**（如配置解析，生成收益不大）。

## 高频追问

**Q1：`go:generate` 和 Makefile 的关系？**
`go:generate` 负责"**声明某个包需要生成什么**"，Makefile / Taskfile 负责"**编排整个项目的构建流程**（顺序、依赖、缓存）"。最佳组合：`go:generate` 写在各包内，Makefile 里一句 `generate: ; go generate ./...`。

**Q2：生成文件要不要写单测？**
不写。**测生成器的源，不测生成物**。比如 mock 的行为由 gomock 库保证；`String()` 由 stringer 保证。对生成物写单测等于重复测第三方工具。

**Q3：怎么避免生成器版本升级导致的大 diff？**
① 用 `go tool` / `tools.go` **锁版本**；② 升级生成器**单独提一个 PR**（纯生成物 diff，便于 review）；③ 在 `.gitattributes` 里折叠 diff。

**Q4：Protobuf 生成物巨大，能只提交源码吗？**
不能——gRPC 服务需要 `.pb.go` 才能编译。**必须提交**。若嫌 diff 大，用 `linguist-generated` 折叠 + 单独 PR。

**Q5：泛型会取代代码生成吗？**
部分会。泛型能替代"类型安全容器、通用算法"这类生成；但**跨语言（Protobuf）、跨文件（mock）、需要编译期枚举展开（stringer）** 的场景泛型做不了，**代码生成仍是不可替代的**。

## 面试话术

> "我们大量用 `go:generate`：枚举用 **stringer**、mock 用 **mockgen**、RPC 用 **buf generate**。工具版本通过 `go get -tool` 锁进 `go.mod`，避免版本漂移。生成物**提交进仓库**方便 review 和离线构建，文件头标 `DO NOT EDIT`，并在 `.gitattributes` 里设 `linguist-generated` 折叠 diff。最关键的是 **CI 里跑 `go generate ./... && git diff --exit-code`**——谁忘了重新生成，PR 直接红，把协作问题挡在合并前。不过我也很克制：**能用泛型或重构解决的，就不引入代码生成**，生成器本身也是技术债。"
