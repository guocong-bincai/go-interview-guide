# 跨团队协作

> 考察频率：★★★★☆  优先级：P1

## 面试官考察意图

考察候选人的**横向领导力和项目推动能力**。

初级工程师：只完成自己模块，别人不配合就抱怨。
高级工程师：**能主动对齐目标、识别依赖、推动决策**，让跨团队项目顺利落地。

面试官想看：你不只是"被安排"做事，而是能主动识别跨团队障碍并解决它。

---

## 核心答案（30 秒版）

跨团队协作的核心是**目标对齐 + 主动暴露风险**：

| 关键动作 | 目的 |
|---------|------|
| 项目启动时明确"我需要谁，谁需要我" | 消除依赖盲区 |
| 用文档而非口头确认关键决策 | 留证据，防扯皮 |
| 周会/双周会同步进度 + 风险 | 提前发现延迟 |
| 提前识别资源冲突并升级 | 不要等到deadline前才说 |

**一句话：** 高级工程师的跨团队能力，体现在"让合作方觉得跟你配合很省心"。

## 深度展开

### 1. 为什么高级工程师必须具备跨团队推进能力

**纯执行层 vs 推进层的区别：**

```
纯执行：我做完我这块就行了
推进层：我要确保整条链路按时交付
```

**5~8 年工程师的典型场景：**
- 依赖中台团队提供 API，要推进他们排期
- 基础设施改造需要 DBA、运维配合
- 跨团队大项目（如大促备战）需要协调产品、测试、运维
- 技术方案评审需要各模块负责人达成共识

**面试中如何讲跨团队能力：**
> "我当时负责交易链路重构，依赖库存服务和营销平台两个团队。我先拉了三方对齐会，把各自的时间节点和风险点书面确认。后来库存团队出现排期冲突，我主动提出接管他们部分联调测试，减少他们的工作量，保证整体进度。"

---

### 2. 如何对齐目标、边界、里程碑

#### 启动阶段：RACIM 模型

每个跨团队项目开始前，用 RACI 明确责任矩阵：

```
R = Responsible（负责执行）
A = Accountable（最终责任人）
C = Consulted（需要咨询）
I = Informed（需要知会）
M = Monitored（需要监督）
```

**实战案例：**
> "大促备战项目，我的职责是：
> - R：交易链路过载保护方案设计 + 实现
> - A：最终对交易链路的可用性负责
> - C：提前咨询缓存团队容量、DB团队索引情况
> - I：每周向技术负责人同步进度
> - M：接受项目经理的进度监督"

#### 里程碑对齐工具

| 工具 | 适用场景 |
|------|---------|
| 共享 Milestone 文档（在线协作文档）| 各方确认关键时间点 |
| 双周同步会 | 持续性跨团队项目 |
| 关键依赖上锁 | 核心接口的排期要对方书面确认 |

**防踩坑：** 口头确认不算数！让对方在共享文档里回复"确认"或发送邮件确认。

### 3. 需求冲突、资源冲突怎么处理

#### 资源冲突处理流程

```
1. 识别冲突（提前识别，不要等到资源被占用）
2. 量化影响：说明冲突会导致什么后果（delay多久，影响哪些功能）
3. 提出方案：不是只说问题，要带着解法
4. 升级对齐：如果协调不了，升级到共同老板
```

**案例：**
> "当时我需要运维团队协助配置新集群，但运维同时被另一个项目占用了。我先评估了如果延后对大促的影响（高风险），然后找了运维负责人，说明我的需求对大促是前置依赖，提出两个方案：① 优先帮我处理 ② 或者安排另一个运维支持。运维负责人评估后决定从另一个项目挪出人手支持我们。"

#### 需求边界冲突

> "产品和运营对某个功能的行为意见不一致，我先梳理了两种方案的利弊和研发成本，然后拉了产品、运营、研发三方会议，让各方明确表态，用会议纪要固化结论。避免了自己私下拍板导致后续扯皮。"

**原则：谁最终承担后果，谁有最终决定权。**

### 4. 如何通过文档、评审、会议推进复杂项目

#### 文档先行

跨团队技术方案评审前，**先写好文档再开会**：

```
Bad: 开会讨论，大家现场想方案
Good: 先发文档，大家预读，会上直接对齐决策
```

**评审文档结构：**
```markdown
## 背景与目标
## 技术方案（带对比）
## 各模块改动点
## 依赖与风险
## 里程碑
## 待确认事项（提前发，让相关方思考）
```

#### 会议节奏

| 会议类型 | 频率 | 时长 | 目的 |
|---------|------|------|------|
| Kickoff 会 | 项目启动 | 1h | RACI 对齐 |
| 周同步会 | 每周 | 30min | 进度 + 风险 |
| 评审会 | 关键节点 | 1~2h | 方案决策 |
| 复盘会 | 项目结束 | 1h | 经验沉淀 |

**开会的核心原则：** 会前有议题，会后有纪要，纪要有行动项和 Deadline。

### 5. 向上管理与横向协同

#### 向上管理：让老板知道你在推动什么

**不要等老板来问你进度，主动汇报：**

> "我每周五会给技术负责人发一份 5 行以内的进度邮件，格式是：① 本周完成 ② 下周计划 ③ 风险点。这样老板心里有数，遇到障碍需要老板协助时也更容易开口。"

**何时需要升级：**
- 跨团队协调不了的问题（超过2周无法推进）
- 资源缺口会影响 deadline
- 技术方案有重大风险

**升级不是告状，是寻求资源：**
> "X 模块的负责人说排期要到下个月，但我们依赖他们的接口没法delay。我跟双方老板都汇报了情况，最后两边老板协调把他们的优先级调高了一档。"

#### 横向协同：建立技术影响力

**让别人愿意配合你的技巧：**
1. 先帮别人解决问题（技术口碑）
2. 提前知会，不要临时抱佛脚
3. 给对方选择权（方案 A vs 方案 B）
4. 感谢对方的配合（公开认可）

## 高频追问

### Q1：合作方一直不配合怎么办？

**参考答案：**
分情况处理：
- **不了解重要性**：用数据说话，说明不配合对他们的影响
- **确实排期冲突**：提出交换条件或寻找替代方案
- **主观不配合**：找双方老板对齐，书面说明依赖关系和风险

> "我之前遇到过一个中台团队不配合的情况。我先私下沟通了解原因（发现是他们觉得需求不清晰），然后我补充了详细的需求文档和接口协议，再约了他们的技术负责人直接对齐，很快推进了。"

### Q2：两个团队目标冲突怎么办？

**参考答案：**
- 明确各自目标的优先级（业务目标 > 技术目标）
- 寻找共同利益点（"我们一起做成了，对双方都有好处"）
- 上升到共同负责人，不要自己扛

### Q3：如何避免跨团队项目延期？

**参考答案：**
- 关键依赖提前"上锁"（确认排期，书面记录）
- 每两周同步进度，提前识别 delay
- Buffer 不要告诉对方（内部消化）
- 识别单点依赖，准备降级方案

### Q4：跨团队技术方案评审，被其他团队挑战方案怎么办？

**参考答案：**
- 提前 1v1 沟通，了解各方关注点
- 评审时用数据支撑（性能数据、成本数据）
- 如果是纯技术争议，引入第三方技术专家仲裁
- 记住：评审是为了找到最优解，不是为了赢
