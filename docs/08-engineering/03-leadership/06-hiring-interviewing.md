# 招聘与面试：高级工程师如何识别候选人

> 考察频率：★★★☆☆  优先级：P1

## 面试官考察意图

考察候选人是否具备**技术判断力和人才培养意识**。

初级工程师：面试是"被考"，只会答题。
高级工程师：**能设计有区分度的面试题，能识别水货，也能发现潜力股**。

面试官想看：你不仅能通过面试，还能帮公司筛选出真正能解决问题的人。

---

## 核心答案（30 秒版）

识别候选人的核心是**分层考察 + 行为验证**：

| 维度 | 考察什么 | 典型问题 |
|------|---------|---------|
| 技术深度 | 原理理解 vs 只会用 | 追问到说不清楚为止 |
| 工程能力 | 能否交付生产级代码 | 代码实现 + 代码审查 |
| 协作与文化 | 能不能跟团队融合 | 项目经历深挖 |
| 业务理解 | 不只是技术宅 | 技术决策背后的业务逻辑 |

**一句话：** 高级工程师招聘，是找"能跟我一起解决未知问题的人"，不是找"能答出标准答案的人"。

---

## 深度展开

### 1. 面试评价维度：技术深度、工程能力、沟通协作、业务理解

#### 技术深度（P0）

**考察方法：刨根问底，不能停在"会用的程度"**

| 级别 | 回答水平 | 识别信号 |
|------|---------|---------|
| 初级 | 知道"是什么"，不知道"为什么" | 背答案，一追问就慌 |
| 中级 | 知道"怎么用"，知道部分原理 | 能讲清基本原理，但深度不够 |
| 高级 | 知道原理，能讲源码，能说清边界 | 能讲清楚适用场景和不适用场景 |
| 资深 | 能对比竞品，能讲设计取舍 | 能说清楚为什么这个设计在当时是最好的选择 |

**实操追问技巧：**
- "你刚才说用 Redis 做缓存，能讲讲 Redis 的过期策略吗？" → 引入 LRU/TTL 源码
- "你说的 GC 三色标记，能讲讲为什么需要写屏障吗？不加行不行？" → 追问混合写屏障
- "你说 Mutex 是自旋锁，能讲讲什么情况下自旋，什么情况下阻塞？" → 考察是否真正理解

#### 工程能力（P0）

**考察方法：现场写代码 + 代码审查**

**现场写代码看什么：**
```
✅ 边界条件处理（nil、空数组、并发）
✅ 变量命名和函数分解
✅ 错误处理
✅ 是否有"防御性编程"意识
❌ 一写一大坨，不拆分
❌ 不处理错误
❌ 上来就写，不理解题意就动手
```

**代码审查（推荐用于高年级工程师）：**
给候选人一段"看起来正常但有 bug"的代码，让他 code review。
```go
// 这段代码有什么问题？
func GetUserIDs(ids []int64) []User {
    users := make([]User, 0, len(ids))
    for _, id := range ids {
        users = append(users, userDB[int(id)])
    }
    return users
}
```
→ 考察点：是否有边界检查、map 并发安全、error 处理

#### 协作与文化（P1）

**考察方法：项目经历深挖**

STAR 法则深挖：
- **Situation**：项目背景是什么？（不要候选人来编，给他真实场景）
- **Task**：你负责什么？
- **Action**：你具体做了什么？（不是"我们团队做了什么"）
- **Result**：结果如何？有数据吗？

**识别"水货"信号：**
- 项目经历全是大项目，自己只做了很小一部分
- 问到具体技术细节就说"我不清楚，那是另一个同事负责"
- 把团队成果说成自己的（典型：面试造火箭，工作拧螺丝）

**识别"潜力股"信号：**
- 对自己做的部分能讲得很清楚
- 能主动说"这个设计我觉得有改进空间，当时因为 XX 原因没改"
- 对新技术有好奇心，能主动学习

#### 业务理解（P2）

**不是每个工程师都需要很强的业务理解，但5~8年工程师应该能理解技术决策背后的业务原因：**

- "为什么要做这个优化？不做会怎样？"
- "这个功能的产品价值是什么？"
- "如果业务指标下降了，你怎么排查？"

### 2. 如何设计有区分度的问题

#### 原则：一个问题，多个考察层次

**Bad：** "Go 的 GMP 调度是什么？"（能背出来就通过，没有区分度）

**Good（分层提问）：**
```
Level 1：GMP 调度是什么？（基础概念）
Level 2：Work Stealing 是什么？什么时候触发？（理解机制）
Level 3：sysmon 抢占在 Go 1.14 之前是怎么实现的？有什么问题？（源码理解）
Level 4：Go 1.14 的抢占式调度解决了什么问题？你遇到过因为 GC 导致的停顿问题吗？（生产经验）
```

#### 题目设计模板

```markdown
## 问题：描述一个真实场景（不是抽象概念）

### 考察点
- 基础概念（80% 候选人能答）
- 原理理解（50% 候选人能答）
- 生产经验（20% 候选人能答）
- 解决能力（5% 候选人能答）

### 追问路径
- 如果答不上来 → 降级到更基础的问题
- 如果答得很好 → 追问边界情况
```

**区分度题库示例：**

| 题目 | 能答上来的 | 不能答上来的 |
|------|-----------|-------------|
| "讲讲 Go 的 GC 混合写屏障" | 对 GC 有源码级理解 | 只会背三色标记 |
| "Redis 主从复制断了怎么办" | 有实际运维/故障处理经验 | 只会背 binlog |
| "线上 P99 延迟突然升高怎么排查" | 有系统性排障经验 | 没遇到过 |
| "你们项目的技术债是怎么治理的" | 有工程全局视角 | 从没想过 |

### 3. 简历筛选看什么

#### 快速筛选信号（5 秒扫简历）

| 看什么 | 好信号 ✅ | 坏信号 ❌ |
|--------|---------|---------|
| 项目经历 | 具体、量化、有技术细节 | "负责 XX 系统开发"（太笼统）|
| 技术栈 | 有深度、有广度、有关联 | 罗列技术名词，没有上下文 |
| 成长曲线 | 职级/职责逐步提升 | 多年前端突然转 Go |
| 公司背景 | 大厂/知名创业公司 | 不知名小公司，职责描述夸大 |
| 开源/GitHub | 有实质贡献 | 只有一个 README |

#### 深度筛选（简历通过后）

简历过了初筛，不代表技术好，但至少说明：
- 基本功过关
- 有一定项目经历
- 值得花时间面试

### 4. 一轮、二轮、交叉面应该怎么分工

#### 推荐分工模型

| 轮次 | 考察重点 | 时长 | 面试官 |
|------|---------|------|-------|
| 一面（技术基础）| 语言基础 + 数据结构 + 算法（简单/中等）| 45min | 高级工程师 |
| 二面（系统设计）| 架构设计 + 项目深挖 + 生产经验 | 45min | 技术专家/架构师 |
| 三面（交叉面）| 代码实现 + 代码审查 | 45min | 其他团队高级工程师 |
| 四面（HR/VP）| 价值观 + 团队匹配 + 职业规划 | 30min | HR/技术 VP |

**交叉面的价值：** 防止"近亲繁殖"，避免一个面试官的个人偏好影响判断。

#### 各轮面试的侧重点

**一面不要考太难的题：** 如果一面就考 hard 算法题把人挂了，后面的深度考察没机会做。
**二面重点考察项目深度：** 问清楚候选人"在项目中解决了什么问题"，而不是"参与了什么"。
**交叉面重点考察代码质量：** 很多人能说清楚，但写出来的代码一塌糊涂。

### 5. 如何避免只招"会背八股的人"

**八股型候选人特征：**
- 问你任何概念，都能流利背诵
- 但一问到实际场景，就说"这个我没遇到过"
- 代码写得很死板，没有变通

**识别方法：加场景追问**

> "你刚才说 Go 的 channel 是协程安全的，那两个协程同时向一个 channel 发送数据，会有问题吗？"

→ 能答上来的人会考虑 channel 的并发安全性（实际上 channel 内部有锁）；只会背八股的人会说"不会有问题因为是协程安全的"（没理解为什么安全）。

**实操技巧：**
1. **每道基础题，加一个具体场景**
2. **让候选人讲一个真实踩过的坑**
3. **给一个错误答案，看候选人能否纠正**（"我听说 GC 会 Stop the World，你觉得对吗？"）

---

### 6. 反向体现高级工程师的团队建设能力

**面试中展示自己带过人：**
> "我带过 3 个校招工程师的成长，我的做法是：① 第一个月只让他们做代码审查，不写生产代码 ② 第二个月开始做小功能，全程 code review ③ 第三个月开始独立负责模块。"

**识别候选人的培养潜力：**
- 愿意分享知识（主动讲，跟被动问区别很大）
- 对新人有耐心
- 能讲清楚自己是怎么带人的

**高级工程师不只要自己强，还要能复制能力：**
> "我主导推动了团队的代码规范落地，制定了 Go 代码规范文档和 lint 规则，全团队代码 review 效率提升了 30%。"

## 高频追问

### Q1：候选人基础很好但项目经历很水，怎么判断？

**参考答案：**
追问项目中的具体技术决策：
- "这个功能的技术方案是你定的吗？为什么这么选？"
- "遇到过什么困难？怎么解决的？"
- "这个项目如果让你重来，你会做什么改进？"

如果全程只能说大框架，说不清楚自己的具体贡献，基本是在"参与"而不是"负责"。

### Q2：候选人技术很强但沟通感觉很自我，怎么判断是否合适？

**参考答案：**
- 给他一道开放性系统设计题，看他是否愿意接受不同意见
- 问他在过去团队中的角色，是单干还是协作
- 观察他是否愿意解释技术问题（有些人技术强但不愿意教人）

> "技术很强但很难合作的'刺头'，对团队的伤害可能大于贡献。5~8 年工程师，协作能力和技术能力一样重要。"

### Q3：怎么判断候选人是否会在入职后快速离职？

**参考答案：**
- 问离职原因，看是否有"抱怨前公司"的迹象
- 问职业规划，看这个岗位是否在他的成长路径上
- 问对技术的热情，是真的喜欢还是只是谋生手段

### Q4：没有标准答案的开放题怎么评分？

**参考答案：**
- **不追求标准答案，追求思考过程**
- 看候选人的分析框架：是否系统化
- 看候选人的边界意识：是否知道什么情况下方案会失效
- 看候选人的学习能力：能否从错误中快速调整
