# 架构决策记录（ADR）与文档工程化

> 考察频率：★★★☆☆  优先级：P1
> 关键词：ADR、Architecture Decision Record、文档即代码、RFC、技术决策留痕、onboarding

## 面试官考察意图

"你们团队怎么做技术决策？决策过程有留痕吗？"——中等偏上的**工程素养**题，考察候选人是否有**团队级工程意识**，而不只是个人写代码能力：

1. 是否知道 **ADR（Architecture Decision Record）** 及其价值；
2. **什么时候写 ADR**，什么粒度；
3. **文档即代码**（Markdown 进仓库、随代码 review、版本化）；
4. 技术决策的**可追溯性**与**新人 onboarding** 效率。

**核心立场：一个技术决策如果不写下来，半年后没人记得为什么——于是要么被盲目推翻，要么成了没人敢碰的"祖传代码"。ADR 就是给未来的自己留一份"判决书 + 理由"。**

---

## 核心答案（30 秒版）

**ADR（架构决策记录）**：用**简短、结构化、版本化**的文档，记录**一个**重要技术决策的**背景、选项、决定、后果**。

**标准结构（五段）**：
1. **Title / Status**：标题 + 状态（Proposed / Accepted / Deprecated / Superseded）；
2. **Context**：为什么现在要做这个决策（约束、问题）；
3. **Decision**：决定采用什么；
4. **Alternatives**：考虑过哪些选项、为什么否掉；
5. **Consequences**：正/负后果、遗留问题。

**四条工程纪律**：
1. **ADR 进代码仓库**（`docs/adr/0001-xxx.md`），与代码一起 review、一起版本化；
2. **一个 ADR 一个决策**，短（1~2 页），不写成长篇设计文档；
3. **只增不改**：决策变更时**新增** ADR 把旧的标记 `Superseded by ADR-xxxx`，保留历史；
4. **不做无痕决策**：影响多人/长期的技术选型、接口约定、数据模型变更都应有 ADR。

**一句话**：**ADR 记录"我们当时为什么这么选"，让决策可追溯、可复用、可推翻（有据可依地推翻）。**

## 深度展开

### 一、ADR 模板

```markdown
# ADR-0007: 使用 NATS JetStream 作为内部事件总线

- Status: Accepted
- Date: 2026-10-09
- Deciders: @alice @bob

## Context
订单、库存、通知三个服务需要异步解耦，当前用 DB 轮询，
延迟高（秒级）、DB 压力大。需要低延迟、可持久化、有确认机制的消息中间件。

## Decision
采用 NATS JetStream，主题 `order.events`，至少一次投递 + 消费端幂等。

## Alternatives
- **Kafka**：功能全但运维重，当前消息量（< 1k/s）不值当。
- **RabbitMQ**：可以，但团队已有 NATS 运维经验。
- **保持 DB 轮询**：延迟与 DB 压力无法接受。

## Consequences
- ✅ 延迟降到毫秒级，服务解耦。
- ⚠️ 引入新中间件，需补充监控与运维文档。
- ⚠️ 至少一次投递 → 消费端必须幂等。
```

### 二、什么时候写 ADR（判断标准）

**写**：
- 引入/替换**基础设施**（消息队列、数据库、缓存、网关）；
- **跨服务接口/协议**约定（gRPC vs REST、字段兼容策略）；
- **架构模式**选择（单体 vs 微服务、同步 vs 异步）；
- **不可逆或高成本**的决策（数据模型、分库分表方案）；
- 有争议、需要留证据的**技术选型**。

**不写**：
- 日常代码风格（交给 linter）；
- 局部、低风险、易回退的实现细节；
- 能被一张 PR 说明清楚的小改动。

> 判断一句话：**"半年后新人问'为什么这么设计'，需要一份文档来解释"→ 写 ADR。**

### 三、文档即代码（Docs as Code）

```text
repo/
  docs/
    adr/
      0001-use-postgres.md
      0002-adopt-grpc.md
      0007-nats-jetstream.md
    runbooks/
      oom-troubleshooting.md
    rfc/
      0042-order-split.md
```

**实践要点**：
- **Markdown 进 Git**：与代码同仓库、同 review 流程，变更可 diff、可追溯；
- **编号单调递增**，永不复用；标题里带上决策关键词；
- **CI 校验**：检查 ADR 编号唯一、必填字段（Status/Date/Deciders）齐全；
- **能渲染**：`mkdocs`/`docusaurus` 生成站点，方便非工程同学查阅。

### 四、ADR vs RFC vs 设计文档

| 类型 | 回答什么 | 篇幅 | 时机 |
|---|---|---|---|
| **ADR** | 为什么做这个决策 | 短（1~2 页） | 决策后（或提议时） |
| **RFC** | 具体方案怎么设计（评审用） | 中长 | 大改动前评审 |
| **设计文档** | 完整的系统设计 | 长 | 大型项目启动时 |
| **Runbook** | 出事了怎么操作 | 短、可操作 | 上线后持续维护 |

**关系**：大改动通常是 **RFC 评审 → 通过后落一条 ADR 记录决策**。

### 五、ADR 如何真正活起来（而非变成僵尸文档）

- **纳入 onboarding**：新人第一周读 ADR 目录，快速理解"为什么现在是这样"；
- **决策时写、评审时看**：PR 模板里加一句"是否需要 ADR"；
- **定期回顾**：标记过时（Deprecated/Superseded），清理僵尸 ADR；
- **领导带头**：技术负责人亲自写，团队才会重视；
- **避免形式主义**：短而精，不追求篇幅；写不出"Alternatives"说明还没想清楚。

### 六、常见坑

- **只在群里口头决策** → 半年后无人记得，反复争论；
- **ADR 写成长篇设计文档** → 没人读，失去"短小可查"的价值；
- **改旧 ADR 而不新增** → 历史被抹掉，无法追溯决策演变；
- **ADR 放 Confluence 不进仓库** → 与代码脱节、搜索困难、review 缺位；
- **只写 Decision 不写 Context/Alternatives** → 后人不知道约束，容易盲目推翻。

## 面试话术

> "我们团队有 ADR 机制，就是架构决策记录。原则是**一个 ADR 记录一个决策**，结构是背景、决策、备选项、后果四段，进代码仓库和代码一起 review、一起版本化。最重要的纪律是**只增不改**——决策变了不是改旧文档，而是新增一条 ADR 把旧的标成 Superseded，这样决策的演变历史完整可追溯。触发条件是影响面大、不可逆或高成本的决策，比如换消息队列、定跨服务协议、数据模型变更，日常代码风格就不写、交给 linter。价值有两个：一是半年后有人质疑设计时能拿出当时的理由；二是新人 onboarding 读一遍 ADR 目录，就明白了系统为什么长这样。"

## 高频追问

- **Q：ADR 和设计文档有什么区别？** A：ADR 短、聚焦"为什么做决策"，只增不改；设计文档长、讲"方案怎么实现"，可迭代。
- **Q：小团队有必要吗？** A：有必要但可以极简，一个 `docs/adr/` 目录 + 模板即可，成本很低。
- **Q：怎么防止 ADR 变形式主义？** A：控制在 1~2 页、只记重要决策、纳入 review 和 onboarding，不追求数量。
- **Q：口头决策怎么办？** A：关键决策必须落文，PR 模板加"是否需要 ADR"提示，负责人带头执行。
