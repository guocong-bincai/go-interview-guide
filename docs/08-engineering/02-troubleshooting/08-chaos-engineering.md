# 混沌工程与故障演练

> 考察频率：★★★☆☆  优先级：P1

## 面试官考察意图

考察候选人是否具备**工程韧性思维**——不是等故障发生再救火，而是主动制造故障、验证系统韧性。
高级工程师要能说清楚：**混沌工程的本质是科学实验，不是破坏；如何控制爆炸半径；如何把演练结果变成可落地的改进项**。
面试官想看你是"救火队长"还是"系统性风险治理者"。

---

## 核心答案（30 秒版）

混沌工程是**在可控环境下主动注入故障**，验证系统在各种故障场景下的表现。
与普通压测的区别：压测测的是"能扛多少"，混沌工程测的是"扛不住时会发生什么"。

核心工具：
- **ChaosBlade**：阿里的故障注入平台，支持网络、CPU、磁盘、容器等注入
- **Chaos Mesh**：基于 Kubernetes 的混沌工程平台，声明式配置
- **Gremlin**：海外商业化混沌工程工具

## 深度展开

### 1. 混沌工程 vs 普通压测 vs 故障演练

| 维度 | 混沌工程 | 普通压测 | 故障演练 |
|------|----------|----------|----------|
| **目标** | 发现未知隐患，验证韧性 | 测量性能上限 | 验证预案是否有效 |
| **触发方式** | 随机/定时自动注入 | 人工发起 | 人工或定时触发 |
| **故障类型** | 真实故障（网络、进程宕机） | 负载类故障 | 通常是预案内的场景 |
| **预期结果** | 未知（需要探索） | 已知（QPS/延迟指标） | 已知（预案是否生效） |
| **频率** | 持续性、自动化 | 阶段性 | 季度性 |
| **风险控制** | 爆炸半径精确控制 | 逐步加压 | 提前通知，干系人确认 |

> **混沌工程的本质是科学实验**：先有假设（"如果 X 故障，系统 Y 应该仍可用"），再注入故障，验证假设。

### 2. 常见故障注入方式

#### 2.1 网络故障

```bash
# ChaosBlade：模拟网络延迟
blade create d network delay --time 3000 --interface eth0

# ChaosBlade：模拟网络丢包
blade create d network loss --percent 50 --interface eth0

# ChaosBlade：模拟 DNS 解析失败
blade create d network dns --domain example.com --dns-mode block

# 模拟部分接口不可用（基于 headerselect 或 weight）
```

**常见场景：**
- 接口超时：注入 3-5s 延迟，观察调用方超时配置是否正确
- 服务不可达：丢包 100%，验证熔断/限流是否触发
- 网络分区：模拟部分节点失联，观察分布式一致性表现

#### 2.2 进程/容器故障

```bash
# ChaosBlade：杀掉容器进程（模拟 Pod 被驱逐）
blade create docker process kill --process mysql

# ChaosBlade：CPU 满载
blade create cpu load --percent 100 --timeout 60

# ChaosMesh：模拟 Pod 被删除
kubectl debug nginx-pod --image=chaosmesh/pod-killer:latest
```

**常见场景：**
- 定时压测时杀掉旧 Pod，观察滚动更新是否平滑
- 单节点 CPU 打满，验证是否自动迁移流量

#### 2.3 依赖服务故障

```bash
# 模拟 MySQL 连接数打满
blade create mysql delay --time 5000 --database test_db

# 模拟 Redis 不可用（超时）
blade create redis delay --time 2000 --addr 10.0.0.1:6379

# 模拟第三方 API 超时/异常
# 通常在代码里埋入 chaos-mesh sidecar 注入 HTTP 错误
```

**关键点：** 注入故障时，**必须同时验证监控告警是否触发**。很多团队做了混沌工程但告警没配置，等于白做。

### 3. 如何控制演练风险（爆炸半径）

**核心原则：不能因为演练导致真实故障。**

#### 3.1 分级环境策略

| 环境 | 风险等级 | 可注入故障类型 | 示例 |
|------|----------|----------------|------|
| **测试环境** | 低 | 所有故障均可注入 | 无业务流量 |
| **预发布环境** | 中 | 非核心服务故障 | 有影子流量 |
| **生产环境（低峰）** | 高 | 只注入**可观测**故障，限时恢复 | 有真实用户 |

#### 3.2 熔断保护三板斧

```go
// 1. 演练前：确认所有依赖的监控阈值已配置
// 2. 演练中：实时观察 error rate / latency
// 3. 演练后：5 分钟自动恢复，或手动一键回滚

// 推荐：使用 kubernetes namespace 隔离
// chaos-mesh 可以在 namespace 级别注入故障，不影响其他业务
apiVersion: v1
kind: Namespace
metadata:
  name: chaos-experiment
```

#### 3.3 演练前 checklist

```
[ ] 通知相关团队（至少 2 人知晓）
[ ] 确认回滚方案已测试
[ ] 监控大盘已打开（基础指标）
[ ] 预计影响时长 < 30 分钟
[ ] 故障注入点：非核心业务
[ ] 恢复时间：< 5 分钟（超时立即停止）
[ ] 通知相关方：SRE / 业务负责人
```

### 4. 演练前、中、后的观测与回滚方案

#### 4.1 演练前：确定"成功标准"

```
假设：如果 user-api 的 QPS 下降 50%，支付系统应该自动降级（不影响下单）
验证指标：
  - ✅ 支付降级提示出现
  - ✅ 用户仍可浏览商品（未级联失败）
  - ❌ 订单金额为 0（不应该发生）
```

**没有假设的演练等于放烟花——看起来热闹，没学到东西。**

#### 4.2 演练中：实时监控

```bash
# 监控核心指标
watch -n 5 'curl -s localhost:9090/metrics | grep http_requests_total'

# 关注黄金指标（USE 方法）
# Utilization（利用率）、Saturation（饱和度）、Errors（错误率）

# 告警阈值（立即停止条件）
# - 错误率 > 5%（正常 < 0.1%）
# - P99 延迟 > 3s（正常 < 200ms）
# - 核心服务不可用 > 2 分钟
```

#### 4.3 演练后：复盘与改进

**复盘报告模板：**

```markdown
## 故障演练复盘 - 2026-05-06

### 基本信息
- 演练服务：user-api
- 注入故障：MySQL 连接延迟 3s
- 演练时长：8 分钟
- 影响范围：约 3% 用户请求失败

### 假设验证
- ✅ 假设成立：超时配置 5s，触发降级
- ❌ 新发现：降级逻辑未写入日志，难以排查

### 改进项（入 issue 跟踪）
1. [ ] 降级逻辑增加结构化日志（P1）
2. [ ] MySQL 超时配置从 5s 降为 3s（P2）
3. [ ] 增加数据库连接池熔断（P1）
```

### 5. 如何把演练结果变成治理项

**混沌工程最大的价值不是发现一个问题，而是建立持续验证机制。**

#### 5.1 建立"韧性评分"体系

```
月度韧性报告 = {
  演练次数: 4 次
  发现隐患: 3 个
  已修复: 2 个
  平均恢复时间: 4.2 分钟（目标 < 5 分钟）
  韧性评分: B+（目标 A）
}
```

#### 5.2 把故障类型变成常态化巡检

```yaml
# 每周自动演练（低风险）
cron: "0 2 * * 1"  # 每周一凌晨 2 点

experiment:
  - name: "数据库连接超时"
    fault: "mysql delay 2000"
    target: "order-service"
    duration: 5m
    expected: "自动降级，错误率 < 5%"
```

#### 5.3 推动文化：让"故障"成为资产

- **故障英雄制**：演练发现重大隐患的人，奖励积分
- **公开复盘**：每月 SRE 例会分享演练结果（匿名化）
- **纳入 SLA**：恢复时间是 SLA 的一部分，混沌工程直接提升 SLA

### 6. 高级工程师如何推动稳定性演练机制

#### 6.1 从"被动救火"到"主动找茬"

```
Level 1: 故障发生 → 修复 → 不再发生（被动）
Level 2: 季度演练 → 发现隐患 → 修复（主动）
Level 3: 持续混沌 → 韧性评分 → 系统性改进（工程化）
```

#### 6.2 推动路径

1. **找切入点**：选一个非核心业务/低峰时段，先做 1-2 次演练
2. **收集证据**：记录演练发现的问题和修复前后的对比（延迟降低 X%、可用性提升 Y%）
3. **汇报价值**：向 CTO/技术 VP 展示"故障注入前后的系统表现对比"
4. **建立制度**：
   - 新服务上线必须有混沌演练报告
   - P0 服务每季度至少 1 次全链路演练
   - 故障复盘必须有"是否可预防"分析

#### 6.3 常见阻力及应对

| 阻力 | 应对策略 |
|------|----------|
| "生产环境演练太危险" | 先在测试环境做，证明价值后再申请预发布环境 |
| "没时间做" | 嵌入到技术规划中，作为稳定性建设的必要项 |
| "老板觉得是破坏性工作" | 改名：叫"系统韧性验证"，用数据说话 |
| "运维团队不配合" | 提供自动化工具（ChaosMesh），降低操作成本 |

## 高频追问

**Q1: 混沌工程和故障演练有什么区别？**
混沌工程更强调"系统性"和"持续性"，是科学实验方法论；故障演练通常是事件驱动的、手工触发的。

**Q2: 如何避免演练本身导致生产故障？**
核心是控制爆炸半径：预发布环境优先、分级注入、设置恢复超时、实时监控。

**Q3: 如果没有 ChaosBlade / ChaosMesh，怎么做混沌工程？**
可以用 iptables（网络故障）、kill -STOP（进程暂停）、tc netem（网络延迟）等 Linux 原生工具，或者直接在代码里埋入试验性开关（Feature Flag）。

**Q4: 演练后系统没挂，是不是说明系统足够健壮？**
不一定——可能是故障注入点选得太轻了。好的混沌工程要"打到痛点"，直到系统暴露出弱点为止。
