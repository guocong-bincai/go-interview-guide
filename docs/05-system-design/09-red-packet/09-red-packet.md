## 1. 核心挑战
- [ ] 高并发：春节微信红包峰值 ~480 亿次请求/天
- [ ] 原子性：总金额不能超发，每人只能抢一次
- [ ] 公平性：随机分配，均值接近平均值
- [ ] 低延迟：用户体验要求 < 200ms

## 2. 拆分算法：二倍均值法
- [ ] 公式：`random(0, 剩余金额/剩余人数 × 2)`
- [ ] 为什么保证均值：数学期望证明
- [ ] 最小值保证（每人至少 1 分钱）
- [ ] Go 代码实现

## 3. 方案一：实时计算（适合小红包）
- [ ] Redis `INCRBY` 扣减剩余金额（原子操作）
- [ ] Redis `SADD` 记录已抢用户（去重）
- [ ] 问题：高并发下 Redis 压力大

## 4. 方案二：预生成队列（适合大红包/秒杀级）
- [ ] 发红包时预先拆分所有金额，存入 Redis List
- [ ] 抢红包：`LPOP` 原子弹出一个金额（天然串行化）
- [ ] 优点：无竞争，性能极高（10W+ QPS）
- [ ] 缺点：需要提前计算，占用 Redis 内存
- [ ] 完整 Go 代码示例

## 5. 防超发设计
- [ ] Redis + Lua 脚本：判断剩余数量 + 扣减原子化
- [ ] 数据库最终一致性校对（异步对账）
- [ ] 幂等性：requestId 防重（同一用户重试不重复扣）

## 6. 数据库设计
- [ ] `red_packet` 表：id/total_amount/total_count/expire_time
- [ ] `red_packet_record` 表：packet_id/user_id/amount/created_at
- [ ] 分库分表：按 packet_id 分片

## 7. 整体架构
- [ ] 发红包流程：拆分 → 存 Redis List → 异步落库
- [ ] 抢红包流程：LPOP → 记录领取 → 异步落库
- [ ] 退款流程：过期未抢完 → 扫描 Redis → 退回发起人
