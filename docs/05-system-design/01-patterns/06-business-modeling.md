# 业务建模方法论

> 考察频率：★★★★☆  优先级：P0

## 面试官考察意图

考察候选人的**业务抽象能力**，这是 5~8 年工程师区别于初中级工程师的核心标志。
初级工程师给需求就写 CRUD，高级工程师先问"这个业务的本质是什么，有哪些实体，边界在哪里"。
面试官想看你：**能不能在短时间内理解一个陌生领域，并把它抽象成可维护的软件模型**。

---

## 核心答案（30 秒版）

业务建模的核心是**找到领域的核心概念和边界**：

| 方法 | 适用场景 |
|------|---------|
| 事件风暴（Event Storming）| 快速理解业务流程，发现领域事件 |
| 核心域 / 支撑域 / 通用域 | 识别业务优先级，把精力集中在核心 |
| 状态机建模 | 识别对象生命周期，明确所有合法状态转换 |
| 限界上下文（Bounded Context）| 划分系统边界，避免领域概念混淆 |

**一句话：** 先理解业务语言，再用代码表达业务概念。

## 深度展开

### 1. 如何从 PRD 提炼领域对象

拿到一份 PRD，先问三个问题：

```
1. 有哪些"参与者"（Actor）？—— 谁在用这个系统？
2. 有哪些"核心业务活动"？—— 参与者做什么？
3. 有哪些"业务对象"？—— 活动的产物是什么？
```

**例子：电商秒杀 PRD**
```
参与者：买家、卖家、平台运营
核心活动：选品 → 秒杀下单 → 支付 → 发货
业务对象：商品、订单、库存、优惠券、账户
```

从这些业务对象中，识别出**实体**和**值对象**：

| 业务对象 | 类型 | 理由 |
|---------|------|------|
| 订单 | 实体 | 有全局唯一ID，生命周期长，跨系统流转 |
| 金额 | 值对象 | 无ID，只描述"多少"，不可变 |
| 收货地址 | 值对象 | 无唯一ID，描述一个地址，可复用 |
| 商品SKU | 实体 | 有唯一编码，价格和库存会变 |

### 2. 核心域 / 支撑域 / 通用域划分

Eric Evans 的 DDD 理论把业务分为三层：

```
┌─────────────────────────────────────┐
│           核心域（Core Domain）      │ ← 公司的核心竞争力，必须做到极致
│  例：抖音的核心域 = 推荐算法 + 内容生态 │
├─────────────────────────────────────┤
│          支撑域（Supporting）         │ ← 业务必须，但非核心竞争力
│  例：电商的核心域 = 交易，支撑域 = 物流 │
├─────────────────────────────────────┤
│          通用域（Generic）            │ ← 放之四海皆准，不用自己做
│  例：认证、支付（用第三方）、短信通知   │
└─────────────────────────────────────┘
```

**面试时怎么讲：**
> "我当时负责的是 XX 项目，核心域是交易撮合（我们的核心竞争力），物流和通知都是支撑域，用第三方服务快速集成，把所有精力都集中在交易引擎的稳定性和性能上。"

### 3. 事件风暴（Event Storming）

事件风暴是一种**多人参与的快速建模工作坊**：

```
步骤：
1. 找一面白板，准备橙色（领域事件）、蓝色（命令/操作）、黄色（聚合）贴纸
2. 参与者（包括业务方！）一起梳理业务流程
3. 沿着时间线贴上所有"发生了什么事"（领域事件）
4. 每个事件前标注"谁触发的"（命令/决策）
5. 识别出每个命令涉及的实体/聚合
6. 发现业务边界（限界上下文）
```

**产出示例（电商下单流程）：**
```
[用户点击下单] → [订单已创建] → [库存已预占] → [支付中] → [支付成功] → [订单已确认]
                            ↓
                   [库存预占失败]
```

### 4. 状态机建模

业务对象的状态转换是最容易出 bug 的地方。**用状态机把每个对象的所有合法状态和转换穷举出来**。

**例子：订单状态机**
```
                    ┌──超时关闭──┐
                    ↓            ↑
创建 ──→ 待支付 ──→ 支付中 ──→ 已支付 ──→ 已发货 ──→ 已完成
  │                                            │
  └────────────取消（用户主动）──────────────────┘
  └────────────取消（客服介入）──────────────────┘

状态转换规则：
- 创建 → 待支付：下单动作
- 待支付 → 支付中：用户发起支付
- 支付中 → 已支付：支付成功回调
- 支付中 → 待支付：支付失败，重试
- 已支付 → 已发货：商家发货
- 已发货 → 已完成：用户确认收货
- (任一非终态) → 取消：用户/客服取消
```

**Go 代码落地：**
```go
type OrderStatus string

const (
    StatusCreated    OrderStatus = "created"    // 初始
    StatusPending   OrderStatus = "pending"    // 待支付
    StatusPaying     OrderStatus = "paying"    // 支付中
    StatusPaid       OrderStatus = "paid"      // 已支付
    StatusShipped    OrderStatus = "shipped"   // 已发货
    StatusCompleted  OrderStatus = "completed" // 已完成
    StatusCancelled  OrderStatus = "cancelled" // 已取消
)

// 状态转换矩阵：当前状态 + 事件 = 目标状态
var orderTransitions = map[OrderStatus]map[string]OrderStatus{
    StatusCreated: {
        "pay":       StatusPending,
        "user_cancel": StatusCancelled,
    },
    StatusPending: {
        "pay_start":  StatusPaying,
        "timeout":    StatusCancelled,
        "user_cancel": StatusCancelled,
    },
    StatusPaying: {
        "pay_success": StatusPaid,
        "pay_fail":    StatusPending, // 支付失败可重试
        "timeout":     StatusCancelled,
    },
    StatusPaid: {
        "ship":         StatusShipped,
        "refund_apply":  StatusRefunding,
    },
    // ... 以此类推
}

func (o *Order) tryTransition(event string) error {
    if next, ok := orderTransitions[o.Status][event]; ok {
        o.Status = next
        return nil
    }
    return fmt.Errorf("invalid transition: %s under status %s", event, o.Status)
}
```

### 5. 把业务边界映射成服务边界

建模的最终目的是**指导系统设计**：

```
业务边界识别          →     服务边界划分
─────────────────────────────────────────
同一业务语言                 同一个微服务
同一聚合根                   同一个数据库
同一团队负责                 同一条部署流水线
变更频率一致                 同一套扩缩容策略
```

**反面案例：**
> 按技术分层拆分（Controller/Service/DAO），导致跨领域数据在同一个 DAO 层耦合。

**正确做法：**
> 按业务领域拆分，每个领域有独立的 API、独立的数据库和自己的聚合根。

## 高频追问

**Q：业务变化快，如何避免模型腐化？**
> 核心是**保持模型的整洁性**：
> 1. 用 `防腐层（Anti-Corruption Layer）` 隔离外部系统对核心模型的侵蚀
> 2. 定期做模型重构，而不是一味叠加 if-else
> 3. 用限界上下文把易变的业务和稳定的业务隔离

**Q：DDD 和传统三层架构怎么选？**
> 小团队（< 10人）、业务简单 → 三层架构足够，不要过度设计
> 大团队（> 30人）、业务复杂、领域边界清晰 → DDD 能减少跨团队沟通成本

**Q：没有业务方配合，怎么做业务建模？**
> 1. 从现有代码和数据库 Schema 反推——看表名、字段名理解业务
> 2. 从线上问题入手——出过问题的流程往往是建模有缺陷的地方
> 3. 从核心 KPI 反推——公司的核心指标背后一定有核心业务实体

## 一句话记忆
**业务建模 = 用事件风暴发现领域事件，用核心/支撑/通用域分配精力，用状态机穷举所有合法转换。**
